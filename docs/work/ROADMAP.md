# dbreplay 로드맵

목표: 운영 DB에 들어온 SQL을 녹화해 샌드박스에 다시 틀고, 변경이 SQL을 얼마나 느리게 만드는지와 대상이
지금 부하의 몇 배까지 버티는지를 잰다. 메이투안의 DB 용량 평가 시스템 글(2025-10-17)이 한 일을 자체 커널이나
전용 인프라 없이, 서버 로그와 명령줄 도구 하나로 따라간다. MySQL 8.4와 PostgreSQL 16이 대상이다.

경위와 조사, 결정의 근거는 [ORIGIN.md](../ORIGIN.md)에 있다.

## 완료

2026-10-11과 10-12에 만들었다. **이 구간은 이슈도 예상도 없이 한 번에 진행했다.** 예상과 실제를 비교할 기록이
없고, 뒤늦게 만들어 넣지 않았다. 코드는 AI 코딩 세션이 썼고 범위와 방향은 범수 님이 정했다(ORIGIN.md 2절).

## 지금의 한계

숫자는 전부 노트북의 도커에서, 원본과 대상이 같은 서버인 상태로 잰 것이다.

- 상한 배속이 실행마다 흔들린다. MySQL에서 같은 절차를 일곱 번 돌려 압축 전 7.50~14.00, 압축 후 1.88~6.00이 나왔고
  압축 후의 수위 판정이 과잉, 적정, 부족으로 갈렸다. PostgreSQL에서는 9.5~13.0 사이에 3.0이 한 번 섞였고 원인을
  모른다. 녹화가 30초다.
- 변환기가 로그를 전부 메모리에 올린다. 초당 26,000문장이면 로그가 한 시간에 약 55GB다(실험 01).
- 재생의 `COMMIT`이 원본의 두 배로 나온 실행이 한 번 있었다(실험 03). 되돌린 직후의 쓰기를 원인으로 짐작했지만
  실험 05에서 다시 만들지 못했고 원인을 모른다.
- 녹화 파일에 리터럴 값이 그대로 남는다. 개인정보가 섞인 SQL을 다룰 방법이 없다.
- 녹화 전부터 열려 있던 연결의 상태(세션 변수, 진행 중이던 트랜잭션)를 알 수 없다.
- 재생기가 프로세스 하나다. 문장 단위로 읽기만 틀면 12배속 위에서 재생기가 먼저 한계에 닿는다(실험 07).
- 실제 운영에서 쓰인 적이 없다.

## 남은 것

예상은 착수 전에 적은 값이고, 예상 마감은 착수할 때 이슈에 적는다. 끝나면 이 표에서 "완료"로 옮긴다.
#2가 예상 6시간에 실제 25분으로 끝났다. 예상을 사람의 작업 시간으로 잡은 탓이다. #7까지의 예상은 그때 적은 값을
지우지 않고 두고, 착수할 때 이슈에 세션 작업 시간으로 다시 적는다. #17부터는 처음부터 세션 작업 시간이다.

## 하지 않는 범위

- 자체 커널 수정으로 녹화하기. 서버 로그를 쓴다.
- Kafka·Flink·ClickHouse 수집 파이프라인과 Kubernetes Job. 파일 하나와 프로세스 하나로 한다.
- 수백 클러스터를 한 화면에서 보는 운영 화면.
- 클라우드 API를 직접 불러 노드를 늘리고 줄이기. 실행은 사용자가 준 명령에 맡긴다.
- MGR, 프록시, 분산 DB, Elasticsearch. 글도 아직 하지 않았다.
