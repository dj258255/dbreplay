## 4. 참고한 글: 메이투안 DB 용량 평가 시스템

- 제목: 从0到1建设美团数据库容量评估系统
- 게시: 2025-10-17, 美团 基础研发平台
- 주소: https://tech.meituan.com/2025/10/17/Database-Capacity-Evaluation-System.html
- 범수 님이 원문 전문을 대화에 붙여 넣어 직접 읽었다. 그림은 보지 못했다.

### 4.1 풀려는 문제

글이 든 고충은 두 가지다.

- 행사 기간에 DB 클러스터의 읽기·쓰기 용량 상한을 정확히 알 수 없어 용량 부족 사고가 난다.
- DB 변경은 운영 사고의 주된 원인인데 위험한 변경을 가려내기 어렵다.

### 4.2 구조: 네 단계

1. **수집**: 자체 커널(MTSQL)이 전량 SQL의 본문, 트랜잭션 ID, 실행 시간을 내보낸다.
   수집기(rds-agent)가 Kafka로 보내고, Flink가 재생 등록된 클러스터의 SQL만 걸러 ClickHouse에 저장한다.
2. **가공**: 처리기(sql-log agent)가 ClickHouse에서 주·종 역할별로 SQL을 읽는다.
   주 DB는 트랜잭션 단위로 묶어 한 실행 단위로 만들고, 종 DB는 SQL 하나씩 독립으로 둔다.
   결과를 트래픽 파일로 만들어 S3에 올린다.
3. **재생**: 재생기(replay-agent)가 S3의 파일을 스트리밍으로 읽어 샌드박스에 튼다.
   재생 작업마다 Kubernetes Job을 하나씩 만든다.
   샌드박스는 녹화 시작 시점의 백업으로 만든 전체 데이터 스냅샷이다.
   재생 전에 "변경 창"을 두어 사용자가 버전 업그레이드, 파라미터 수정, 테이블 구조 변경을 넣는다.
4. **분석과 리포트**: 운영과 샌드박스 양쪽에서 수집한다.
   부하 지표(CPU busy, Load Average, 슬로우 쿼리, 복제 지연), SQL 모양별 실행 시간, 핵심 파라미터와 장비 사양.

### 4.3 세 가지 기능

**트래픽 재생(流量回放)**: 1배속으로 틀어 변경 전후를 비교한다. 리포트는 나빠진 SQL 상위 3개,
좋아진 SQL 상위 3개, 상세 비교를 보여 준다.

**용량 탐색(容量上探)**: 업무 피크 때 녹화한 트래픽을 여러 라운드에 걸쳐 배속을 올리며 튼다.

- 과부하 판정: 사용자가 그 클러스터에 설정한 알람이 울리면 과부하다.
- 라운드마다 샌드박스 데이터를 자동으로 되돌리고, 분석기가 알람을 조회해 다음 배속을 계산한다.
- 1단계(빠른 탐색): 배속을 지수적으로 올려 알람이 울리는 경계를 찾는다.
- 2단계(정밀 보정): 알람이 울린 최소 배속과 울리지 않은 최대 배속 사이를 이분 탐색한다.
  정해 둔 정밀도에 도달하면 끝낸다.
- 용량을 잴 때는 샌드박스 사양을 운영과 똑같이 맞춘다.

**용량 운영(容量运营)**: 여러 클러스터의 수위를 한눈에 본다.

- 수위 = 운영 QPS / 탐색으로 얻은 상한 QPS
- 기본 건강 구간은 30~50%다. 30% 미만은 과잉, 50% 초과는 부족이다.
  50%는 "평소의 2배를 버텨야 한다"는 요구를 뒤집어 적은 값이다.
- 대상은 트래픽 모양이 안정적인 핵심 클러스터로 제한한다.
- 평가 결과에는 유효 기간이 있다. 트래픽 모양, 사양, 버전과 파라미터, 알람 임계가 바뀌면
  무효로 표시하고 다시 잰다.
- 과잉이면 줄일 수 있는 노드를, 부족이면 늘릴 노드 수를 계산해 제안하고, 한 번의 조작으로 실행한다.

### 4.4 배속 재생의 시각 제어

재생기는 트래픽 파일의 SQL마다 실행 코루틴을 하나씩 배정하고, 그 안에서 실행 시각을 맞춘다.

1. 원래 트래픽의 기준 시각을 `sqlBaseTime`으로 둔다.
   SQL의 운영 실행 시각에서 기준 시각을 빼 원래 지연 `originalDelta`를 얻는다.
2. `planDelta = originalDelta / 배속`으로 계획 지연을 구한다.
3. 코루틴이 SQL을 미리 받아 두고(비동기 선취), 그 시점에 재생 시작부터 실제로 흐른 시간
   `realPassDelta`를 잰다.
4. `planDelta >= realPassDelta`이면 그 차이만큼 기다린 뒤 실행한다. 이상적으로는 모든 SQL이 이 가지로 간다.
5. `planDelta < realPassDelta`이면 즉시 실행한다. 이 경우가 많으면 재생기의 동시 처리가 모자라
   재생이 왜곡됐다는 뜻이다.

5번의 비율은 재생기가 스스로 보고할 수 있는 왜곡 지표다. 6절의 충실도 측정이 여기서 시작한다.

### 4.5 글에 나온 수치

두 사례뿐이고 적용 규모는 없다.

- 테이블 압축: 가장 많이 실행되는 SQL이 0.90ms에서 0.97ms로, 저장 공간은 원래의 40%로.
- 사양 축소: 축소한 사양에서 6배가 넘어야 알람이 울렸다. 요구는 2배여서 축소했다.

### 4.6 기존 방식의 한계 (글의 주장)

| 기존 방식 | 한계 |
|---|---|
| 지표로 계산 | 트래픽과 지표가 엄밀한 선형이 아니라 상한 예측이 부정확하다 |
| 전체 링크 부하 테스트 | 서비스 요청을 녹화해 재생하므로 전 구간 병목은 찾지만, DB에 닿는 트래픽은 시나리오 복잡도와 표본 풍부도에 좌우돼 실제와 같아지기 어렵다. 서비스 쪽 개조 비용도 든다 |
| 고정 규칙 검사 | 인덱스 추가, 컬럼 타입 변경 같은 일반 변경은 걸러지지 않는데 SQL 효율이 나빠질 수 있다 |
| 오프라인 테스트 | 오프라인과 운영의 데이터가 다르고 테스트가 충분하지 않다 |

전체 링크 부하 테스트와 이 시스템의 차이는 녹화하는 층이다. 앞은 서비스 요청을, 뒤는 DB에 도착한 SQL을 녹화한다.

### 4.7 글에 적힌 제약과 계획

- 현재는 MySQL 주종 구성만 지원한다. 향후 MGR, Proxy, 자체 분산 DB(Blade), Elasticsearch를 계획한다.
- 향후 계획: 예산 계획 연계, 용량 병목 자동 분석과 재검증, 대형 행사·사고 사례 보관소(데이터 스냅샷, SQL 트래픽, 설정).
- 기존 오픈소스 재생 도구는 한 번도 언급하지 않는다. 자체 개발한 이유도 적지 않았다.

## 5. 왜 새 저장소인가

대화 초반에는 Claude가 새 프로젝트를 반대했다. 그 반대는 관제 플랫폼을 하나 더 만드는 경우였다.
재생 도구는 다음 이유로 사정이 다르다고 결론을 바꿨다.

- **원칙이 충돌한다.** DBTower는 대상 DB에 조회 계정으로만 붙고 임의 변경을 하지 않는다.
  재생은 녹화를 위해 대상 설정을 건드리고 샌드박스에 쓰기를 쏟아붓는다.
- **성격이 다른 프로그램이다.** DBTower는 오래 떠 있는 관리 서버이고, 재생기는 시각을 맞춰
  부하를 쏘고 끝나는 실행 도구다. gh-ost나 pt-upgrade 같은 명령줄 도구가 자연스러운 형태다.
- **겹치는 것이 없다.** 등록, 수집, 알림, 화면을 다시 만들 일이 없다.
- **빈자리가 있다.** MySQL 쪽은 유지되는 재생 엔진이 마땅치 않다(7절).
- **릴리스가 섞이지 않는다.** DBTower는 한 릴리스를 한 이야기로 묶는다.

나중에 DBTower와 잇는 길은 이미 선례가 있다. DBTower의 `onlineddl` 모듈은 gh-ost를 감싸고 승인과
상태 추적을 얹었다. 같은 방식으로 변경 티켓에 재생 결과를 붙이는 쪽만 DBTower에 두면 된다.

Java 21을 제안한 근거: 메이투안 재생기는 SQL마다 코루틴 하나를 배정한다. Java 21의 가상 스레드가
같은 모양이라 Go가 아니어도 같은 설계가 된다.

## 6. 제안된 범위

차별점은 측정이어야 한다. 메이투안 글도 기존 도구들도 "재생이 원본과 얼마나 같은가"를
수치로 내놓지 않았다. 글은 왜곡이 생길 수 있다고만 적었다.

한 덩어리로 완결되는 범위는 네 가지다.

1. 녹화 방식과 무관한 트래픽 파일 형식, 그리고 로그를 그 형식으로 바꾸는 변환기
2. 재생기: 배속 제어, 트랜잭션 단위 묶음, 세션 대응
3. 전후 비교 리포트: 쿼리 모양별 지연 차이
4. 충실도 측정: 원본과 재생의 QPS 곡선, 지연 분포가 얼마나 일치하는지

빼는 것: 샌드박스 자동 구축, 용량 탐색 반복 운영, 화면.

녹화를 파일 형식 뒤로 숨기면 가장 어려운 결정(로그냐 패킷이냐)을 미룰 수 있다.
첫 변환기는 로그 하나로 시작하고, 나머지는 같은 형식을 내는 변환기를 더하면 된다.

서버 로그로 시작하자는 이유: 도커에서 바로 재현되고, 패킷 캡처처럼 호스트 권한이나 암호화 연결
문제에 걸리지 않는다. 대신 로그를 켰을 때 대상에 붙는 부하는 재서 함께 적어야 한다.

### 국내

카카오 MRTE(MySQL Realtime Traffic Emulator) 하나를 확인했다.

- 수집기가 DB 서버에서 지정 포트로 들어오는 패킷을 pcap으로 캡처해 소스 IP, 소스 포트, 페이로드를
  RabbitMQ로 보낸다. 재생기가 그것을 테스트 서버에 튼다. 수집기는 Go로 작성됐다.
- 카카오 DB팀의 2016-06-09 글 "MySQL CPU Saturation Analysis"에 사용 사례가 있다.
  CPU 포화 장애의 원인을 찾으려고 운영 서버의 SELECT 트래픽만 테스트 서버로 보냈고 같은 증상이 재현됐다.
- README의 제약: 서버 측 prepared statement는 캡처되지 않는다. 원격 서버의 패킷은 못 잡으므로
  수집기를 DB 서버 위에서 돌려야 한다.

네이버, 토스, 우아한형제들, 라인, 당근 등의 공개 사례는 검색에서 찾지 못했다. 없다는 뜻은 아니다.

### 조사에서 읽어 낸 것

- 도구를 가르는 기준은 녹화 방식 네 가지다.
  로그는 대상 설정을 바꿔야 하고 부하가 붙는다.
  패킷은 DB 서버에 직접 올라가야 하고 암호화 연결을 못 읽는다.
  프록시는 경로에 프록시가 있어야 한다.
  커널은 자체 엔진이 있어야 한다.
- 오픈소스가 자주 멈춘다. 재생은 업그레이드나 이전 때 한 번 강하게 필요하고 끝나면 유지할 동기가
  사라진다. pgreplay-go도 MRTE도 특정 프로젝트나 장애 때문에 만들어졌다.
- 살아남은 것(Oracle, 알리바바 DAS, TiProxy, 메이투안)은 녹화 지점을 자기가 가진 쪽이다.

## 8. 걱정과 한계

- **같은 무덤에 갈 수 있다.** 재생기를 하나 더 만드는 것만으로는 MRTE나 Percona Playback과 같은 결말이다.
  그래서 차별점을 충실도 측정에 뒀다.
- **크기가 크다.** 시각 제어, 동시성, 트랜잭션 묶음을 제대로 맞추는 일은 DBTower의 세 항목(9절)과
  비교가 안 되게 크다.
- **배속 재생은 실제 증가와 다르다.** 같은 요청을 빨리 트는 것이라 접근하는 데이터 범위는 그대로이고
  간격만 줄어든다. 사용자가 늘면 건드리는 데이터도 넓어져 캐시 적중률이 달라진다.
  재생으로 얻은 상한은 "이 트래픽 모양이 유지될 때"라는 조건이 붙는다.
- **절대 용량은 같은 사양에서만 의미가 있다.** 노트북에서 잰 상한은 쓸 수 없고, 전후 차이만 의미가 있다.
- **녹화 파일에 실제 값이 들어간다.** 개인정보가 섞인 SQL이 그대로 파일이 된다. 메이투안 글은
  보호 방법을 말하지 않는다. 이 도구는 답을 가져야 한다.
- **혼자 만든 도구는 실제 운영에서 쓰였다는 증거가 없다.** 재현 가능한 시나리오로 대신해야 한다.

## 9. DBTower와의 관계

DBTower는 5기종(MySQL, PostgreSQL, SQL Server, Oracle, MongoDB) DB 운영 플랫폼이고, 1차 지원 대상
직무는 DBMS 운영 관리 플랫폼이다. 이 저장소는 그 옆에 서는 독립 도구다.

같은 대화에서 DBTower에 넣을 만하다고 뽑은 항목이 셋 있다. 이 저장소의 일이 아니고, 착수 여부도
정해지지 않았다. 여기 적는 이유는 두 일을 헷갈리지 않기 위해서다.

1. MDL 락을 쥔 세션 찾기. DBTower의 MySQL 구현은 막는 세션을 `sys.innodb_lock_waits`에서만 찾아,
   DDL이 오래된 트랜잭션에 막힌 경우 대기 문구만 보이고 누가 막는지는 비어 있다.
2. 복제 지연의 원인 분해. 지금은 30초 임계 알림만 있다.
3. 이상 감지를 z-score에서 MAD로 바꿀지 비교 실험. 지금은 요일×시간대 버킷의 평균과 표준편차로
   `z >= 3.0`을 본다. 베이스라인이 요약값을 합치는 구조라 중앙값을 쓰려면 저장 형태를 바꿔야 한다.

다만 이력 테이블은 스레드당 보관 개수가 정해진 원형 버퍼라 문장이 많은 트랜잭션은 앞부분이 밀려 나간다.
이 내용은 Claude가 기억으로 말한 것이고 실물로 확인하지 않았다.

## 11. 대화에서 틀렸다가 고친 것

같은 실수를 반복하지 않으려고 남긴다.

- "부하 테스트는 사람이 짠 트래픽"이라고 했다가 고쳤다. 메이투안의 전체 링크 부하 테스트도 녹화 후
  재생이다. 차이는 녹화하는 층이다.
- "커널 패치는 회사에 가도 쓸 일이 없다"고 했다가 고쳤다. 커널 팀이 있는 회사에서는 실무다.
  메이투안 글의 저자는 커널을 고치는 사람이 아니라 커널 팀과 협업해 플랫폼을 만드는 사람이다.
- "재생 엔진은 기존 것을 감싸면 된다"고 했다가 고쳤다. 조사해 보니 MySQL 쪽은 감쌀 만큼 유지되는
  엔진이 마땅치 않았다.
- "새 프로젝트는 만들지 않는 편이 맞다"고 했다가, 재생 도구에 한해 새 저장소가 맞다고 바꿨다.
- 제안한 작은 검증 작업을 "그 실험"이라고 불러 메이투안 글 자체가 실험인 것처럼 들리게 했다.

## 12. 확인하지 못한 것

- pt-upgrade와 pgreplay의 현재 유지보수 상태
- MRTE 재생기(MRTE-player)의 구현 언어와 세부. 카카오 기술블로그의 소개 글은 본문이 열리지 않았다
- 임계 0의 슬로우 로그가 대상에 붙이는 부하. 실험 01에서 노트북 도커 기준으로 쟀다. 처리량이 평균 7%
  낮았으나 실행 간 편차와 같은 크기였다. 운영급 장비에서는 재지 않았다.
- (확인됨) MySQL 슬로우 로그만으로 트랜잭션 경계를 복원할 수 있는지. 실험 01에서 문장 37개가 서버의
  정답지와 전부 일치했다. 조건과 한계는 `experiments/01-log-feasibility/README.md`에 있다.
- 화웨이 클라우드 DRS에 트래픽 재생 문서가 있다는 것은 검색 결과의 주소로만 봤고 내용은 읽지 않았다
- 지원하려는 회사가 MySQL과 PostgreSQL을 얼마나 쓰는지

## 13. 2차 조사와 논의 (2026-10-11, 이 저장소의 대화)

웹 검색으로 확인했다. 각 페이지는 요약 도구를 거쳐 읽었고 원문을 직접 보지는 못했다.

### 수요가 있다는 쪽

- GitLab이 GitLab.com용 SQL 트래픽 재생 도구를 직접 만들고 있다(에픽 17719, 2025-12-02 상태 노트 기준
  진행 중). 목적은 DB 용량 측정과 샤딩·분할·버전 업그레이드의 사전 측정이고, 1배속과 1.5배속 재생이
  완료 기준이다. 모든 문장을 로그로 남기는 방식은 자기들 쿼리량에서 운영을 해칠 수 있다고 보고
  애플리케이션에서 쿼리를 떠 보내는 방식을 택했다. 설계 문서 본문은 읽지 못했다.
- 알리바바 클라우드는 PolarDB MySQL 대버전 업그레이드 전 트래픽 재생과 압측을 유료 기능으로 판다.
  1~30배속, SQL 템플릿별 전후 비교, 기준 데이터 이관 자동화가 들어 있다.
- 페이스북은 MyRocks 이전 때 운영 트래픽을 녹화해 테스트 인스턴스에 트는 섀도 테스트 프레임워크를
  만들었다(The New Stack의 2차 서술).
- Percona 포럼(2023-04)의 답변: query-playback은 최근 활발히 개발되지 않는다. 정확한 재생은 로그 전체를
  파싱해 트랜잭션을 가려내고 간격과 순서를 정해야 해서 매우 어렵고, 그래서 도구들이 나왔다 사라졌다.

### 재생 없이 하는 쪽

- Uber(2,100개 이상 클러스터)와 GitHub(1,200대 이상)는 MySQL 8.0 업그레이드에 재생을 쓰지 않았다.
  새 버전 복제본을 옆에 붙여 운영 읽기 트래픽을 받게 하고 지켜본 뒤 승격했다. Uber는 승격 뒤 일부
  클러스터에서 실행 계획이 바뀌어 지연이 늘었다고 적었다.
- 이 방법은 쓰기 경로, 파라미터·인덱스·사양 변경, 용량 상한을 재지 못한다. 이 도구가 쓸모 있는 자리는
  그쪽이다.

### 국내

- 재생으로 업그레이드나 용량을 검증했다는 공개 사례는 찾지 못했다. 회사 기술블로그 도메인만 지정한
  검색에서도 같았다. 없다는 뜻은 아니다.
- 보이는 것은 합성 부하(우아한형제들의 sysbench TPC-C), 데이터 정합성 비교(LY의 주문 DB 이전),
  점검표(카카오클라우드의 8.4 전환 안내)다.
- MRTE-Player는 트랜잭션 순서를 보장하지 못한다고 적혀 있다.
- DBA 채용 공고에는 "정기 패치·업그레이드 사전점검 및 사후 검증", "반복 운영업무 자동화", "BMT"가 담당
  업무로 나온다.

### 오픈소스 재확인

- 2024~2025년에 나온 MySQL 전용 재생 도구는 검색에서 찾지 못했다. MySQL 8.4에 내장된 재생 기능도
  찾지 못했다.
- Claude가 기억으로 말한 "PolarDB의 frodo"는 GitHub에서 찾지 못했다. 알리바바 클라우드 이전 도구
  (mysqlsniffer) 문서의 설치 경로에 그 이름이 보일 뿐이고, 그 도구는 문의해야 받는 비공개다.

### 실험 02의 결과

- 녹화한 sysbench 트래픽을 같은 서버에 다시 틀었다. 2배속까지 초 단위 문장 수의 차이가 평균 0.3% 이하였고,
  8배속에서 포화했다. 재생 오류는 0개였다(`experiments/02-replay-fidelity/README.md`).
- 덤프로 되돌린 직후에는 InnoDB 통계가 틀어져 실행 계획이 바뀔 수 있다. 되돌린 뒤 통계를 다시 잡아야 한다.
- 원본의 실행 시간은 서버가 잰 값이고 재생의 실행 시간은 재생기가 잰 왕복 시간이다. 전후 비교는 재생
  중에도 대상의 슬로우 로그를 켜서 로그끼리 해야 한다.
- 재생기는 DB 옆에서 돌려야 한다. 도커 포트 포워딩을 거치면 문장 왕복이 0.17ms에서 0.59ms로 늘었다.

### 실험 03과 04의 결과

- MySQL에서 테이블 압축 전후를 비교했다. 평균 실행 시간이 0.118ms에서 0.200ms로 늘었고 `INSERT`가 6~7배가
  됐다. 버티는 배속은 5.00에서 4.25로 내려갔다(`experiments/03-mysql-compare-explore/README.md`).
- PostgreSQL에서 같은 흐름이 전부 돌았다. 문장 41,234개가 오류 없이 재생됐고, `synchronous_commit`을 끄자
  `END`가 92.7% 줄었으며, 상한은 19배속이었다(`experiments/04-postgres/README.md`).
- Connector/J는 쓰기 문장마다 `SELECT @@session.transaction_read_only`를 먼저 보낸다. 재생기가
  `useLocalSessionState=true`를 기본으로 넣게 고쳤다.
- 원본이 준비된 문장을 쓴 경우 원본 로그와 재생 로그는 직접 비교가 안 된다. 원본은 실행 단계만 찍히고 재생은
  파싱까지 한 줄에 들어간다. 비교는 재생끼리 한다.
- PostgreSQL 로그의 시각은 밀리초 단위라 문장의 시작 시각이 1ms 안에서 뭉친다. 한 연결 안의 순서는 지켜진다.
- 쉬고 있던 가상 스레드가 계획 시각보다 1ms 넘게 늦게 깨어나는 일이 있다. PostgreSQL 실험에서 문장의 5~10%였다.
  고치지 않았다.

### 글의 기준을 다시 읽은 결과 (2026-10-12)

기준과 숫자만 뽑게 해서 글을 두 번 더 읽었다. 요약 도구를 거친 것이다.

- 과부하: "사용자가 업무에 맞게 클러스터에 알람 정책을 걸고, 알람이 울리면 과부하". 알람의 항목과 임계값은 없다.
- 수집하는 부하 지표로 CPU busy, Load Average, 슬로우 쿼리, 복제 지연이 나온다. 임계값은 없다.
- 탐색: 지수로 올린 뒤 이분. 시작 배속, 배수, 정밀도의 값, 라운드 수 제한은 없다.
- 왜곡: 계획 시각을 지나 즉시 실행된 문장이 "대량"이면 왜곡 가능. 허용 비율은 없다.
- 리포트: SQL 템플릿별 실행 시간, 나빠진 SQL과 좋아진 SQL 각 상위 3개. 순위의 기준은 없다.
- 수위: 식과 기본 구간 [30%, 50%]가 나온다. 50%는 평소의 2배를 버틴다는 뜻이고 30%의 근거는 없다.
- 평가: 만료 시각이 있다(일수는 없다). 트래픽 모양, 하드웨어 사양, 버전과 파라미터, 알람 임계값이 바뀌면 무효.
- 수집 필드: SQL 본문, 트랜잭션 ID, 실행 시간. 주 DB는 트랜잭션 단위로, 종 DB는 SQL 독립으로 처리.
- 글의 숫자는 0.90ms → 0.97ms, 40%, 6배, 2배, 30~50%, 상위 3개, 1배속이 전부다.

### 글의 방식으로 바꾼 뒤의 결과

- 재생 단위를 트랜잭션으로 바꾸자 대상이 밀릴 때 실행 중인 연결이 수백 개로 쌓였다. 연결 단위에서는 대상이
  느려지면 부하도 함께 줄어 이런 모습이 나오지 않았다.
- MySQL: 알람 없이 버틴 배속이 테이블 압축 전 8.50, 후 3.75였다. 한 번 더 돌렸을 때는 7.50과 2.75였다.
  방향은 같고 절대값은 흔들린다(`experiments/03-mysql-compare-explore/README.md`).
- PostgreSQL: 9.5배속이었다(`experiments/04-postgres/README.md`).
- 운영체제 타이머로는 가상 스레드가 계획 시각보다 중앙값 0.76ms 늦게 깼다. 전용 스레드가 돌면서 깨우게
  바꿔 0.03ms가 됐다. 그 타이머에 대기자를 잘못 꺼내는 버그가 있어 PostgreSQL 실험이 한 번 멈췄고 고쳤다.
- 문장 단위로 쓰기 트래픽을 틀면 순서가 바뀌어 실패가 난다(244개). 읽기에만 써야 한다.
- 덤프로 되돌린 직후에는 서버가 쓰기를 내리는 중이라 `COMMIT`이 원본의 두 배로 나왔다. 되돌린 뒤 기다리는
  단계가 없다.

### 메이투안 글과의 대응

| 글의 기능 | 이 저장소 | 상태 |
|---|---|---|
| 수집과 가공 | `dbreplay convert` (MySQL 슬로우 로그, PostgreSQL csvlog) | 있다. 글은 커널을 고쳐 수집하고 이 저장소는 서버 로그를 읽는다. 메모리에 안 들어가는 로그는 12GB까지 확인했다(실험 10) |
| 주 DB는 트랜잭션 단위, 종 DB는 SQL 독립 | `--unit transaction`, 종 DB의 트래픽은 `--replica-trace`로 함께 | 있다. 주종이 한 장비에 있는 구성에서만 돌려 봤다(실험 11) |
| 배속 재생과 왜곡 판정 | `dbreplay replay`, 재생기가 늦은 문장의 비율 | 있다. 재생기가 프로세스 하나라 읽기만 틀면 12배속 위에서 재생기가 먼저 막힌다(실험 07) |
| 트래픽 재생: 변경 전후 비교, 나빠진·좋아진 SQL 상위 3개 | `dbreplay compare`, `dbreplay report` | 있다. 읽은 행 수, 오류의 변화, 새로 실패한 문장도 낸다. 한 번의 비교는 변경과 무관한 모양도 20~40% 오르내린다(실험 09, 13) |
| 인덱스 변경, 버전 업그레이드, 파라미터 튜닝의 검증 | 위의 비교를 그 장면에 쓴다 | 세 장면을 전후 3번씩 돌려 봤다(실험 09). 서버 성능 비교는 장비가 하나라 하지 못했다 |
| 용량 탐색: 알람으로 과부하 판정, 지수 뒤 이분, 라운드마다 되돌리기 | `dbreplay explore` | 있다. 알람은 사용자가 준 명령이나 지표의 기준이다. 상한이 실행마다 흔들린다(#10) |
| 용량 운영: 수위와 건강 구간, 읽기와 쓰기의 수위 | `dbreplay explore`의 끝에 출력 | 있다. 구간은 옵션으로 바꾼다. 읽기만의 상한은 구하지 못했다(실험 07) |
| 평가의 유효 기간과 무효 처리 | `dbreplay explore --out`, `dbreplay check` | 있다. 하드웨어 사양은 확인하지 못한다 |
| 운영과 샌드박스의 부하 지표 수집 | 실행 중인 연결, 느린 문장, 복제 지연을 DB에서. CPU와 Load Average는 사용자 명령으로 | 있다. 글의 지표 체계에 붙는 것이 아니라 도구가 직접 뜬다 |
| 샌드박스 자동 구축과 되돌리기 | `--snapshot`, `dbreplay reset` | 되돌리기만 있다. 논리 덤프를 되붓는다. 샌드박스를 띄우는 일은 하지 않는다 |
| 위탁 평가, 만료 시 자동 재평가 | `dbreplay manage` | 대상 목록을 훑어 필요한 것만 다시 평가한다. 떠 있는 프로세스가 아니라서 주기 실행은 cron 같은 것에 건다 |
| 확장·축소 제안과 자동 실행 | `explore --read-nodes`, `--scale-command` | 권고는 낸다. 읽기 상한이 노드 수에 비례한다는 가정이고 확인하지 않았다. 실행은 사용자 명령에 맡기고 의심스러우면 실행하지 않는다 |
| (글에 없음) 녹화 파일의 개인정보 | `convert --mask strings` | 글자 값과 긴 숫자를 가린다. 어떤 열이 개인정보인지는 모른다(실험 13) |

2026-10-12의 상태다. 수치는 전부 노트북의 도커에서 나왔다. 글의 조건(서버가 따로인 구성, 운영급 장비, 수백 클러스터)에서
확인한 것은 하나도 없다.

### 범위에 대한 논의

- 메이투안 글의 중심은 용량 탐색과 용량 운영이고, 트래픽 재생은 그 밑의 기반 기능이다. 6절의 제안은
  기반 기능만 떼어 낸 것이다.
- 글의 중심을 따라가려면 첫 완결 시나리오를 "변경 전후의 버티는 배속 비교"로 잡고, 데이터 되돌리기와
  탐색 반복을 범위에 넣어야 한다. 범수 님은 이쪽에 관심을 보였으나 확정하지 않았다.
- 글의 과부하 판정은 이미 설정된 알람에 기댄다. 이 도구는 무엇을 과부하로 볼지 직접 정해야 한다.
