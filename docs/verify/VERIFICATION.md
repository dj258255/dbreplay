# 검증 기록

어느 기능을 무엇으로 확인했는지의 색인이다. 명령과 출력, 조건, 한계는 각 실험의 README에 있다.
새로 확인한 것이 생기면 표에 한 줄을 더한다.

단위 테스트는 `./gradlew test`로 돈다. 2026-10-12 기준 83개다. 실험은 도커가 필요하고 CI에서 돌지 않는다.

| 확인한 것 | 결과 | 어디서 | 반복 |
|---|---|---|---|
| MySQL 슬로우 로그로 트랜잭션 경계가 복원된다 | 문장 37개가 `performance_schema`의 기록과 전부 일치 | 실험 01, `SlowLogConverterTest` | 1회, 테스트로 고정 |
| 임계 0의 슬로우 로그가 붙이는 부하 | 처리량 -6.9% (편차 7~9%와 구분되지 않음) | 실험 01 | 3회 |
| 바이너리 프로토콜의 준비된 문장이 값이 채워진 SQL로 남는다 | sysbench 로그에서 확인 | 실험 01 | 1회 |
| `use db;` 줄은 연결이 아니라 로그 파일 기준으로 찍힌다 | 세 연결을 섞어 확인 | 실험 01, `SlowLogConverterTest` | 1회, 테스트로 고정 |
| 연결 단위 재생이 2배속까지 원본과 같게 나간다 | 초 단위 문장 수 차이 평균 0.18~0.33% | 실험 02 | 배속마다 1회 |
| 되돌린 직후의 통계가 실행 계획을 바꾼다 | `sbtest1` 범위 조회 59µs → 16.8ms, `ANALYZE` 뒤 복구 | 실험 02 | 1회 |
| Connector/J가 쓰기 문장마다 조회를 끼워 넣는다 | 118,822문장에 23,764번 | 실험 03 | 1회 |
| 테이블 압축 전후의 SQL 모양별 차이 | `INSERT` +515~614%, 한 행 조회 +97~125%. `COMMIT`은 부호가 갈림 | 실험 03 | 4회 |
| 알람 기준 용량 탐색 (MySQL) | 압축 전 7.50~10.00배속, 후 1.88~5.00배속. 수위 판정이 실행마다 갈림 | 실험 03 | 5회 |
| 문장 단위 재생은 쓰기 순서를 지키지 못한다 | 약 108,000문장 중 244~651개 실패 | 실험 03 | 5회 |
| 도구가 샌드박스를 되돌린다 (#4) | MySQL 40만 행 3.4~5.6초, PostgreSQL 50만 행 1.0초. 바꿔 둔 1,000행이 원래대로 돌아옴 | 실험 05, `SandboxTest` | MySQL 7회, PostgreSQL 1회 |
| 되돌린 뒤 기다리면 재생의 `COMMIT`이 원본에 가까워진다 | 확인하지 못함. 배율이 기다리지 않으면 0.88~1.17, 기다리면 0.91~1.02 | 실험 05 | 조건마다 3회 |
| PostgreSQL에서 되돌린 뒤 체크포인트를 일으키면 재생의 WAL이 는다 | 3.0MB → 45.5MB (전체 페이지 이미지 0 → 약 5,640). 상한은 13 대 12로 비슷 | 실험 05 | 재생 2회, 탐색 1회 |
| 평가의 유효성 확인 | 파라미터와 알람 기준을 바꾸면 무효로 답한다 | 실험 03, `EvaluationTest` | 1회, 테스트로 고정 |
| PostgreSQL csvlog 변환과 인자 끼워 넣기 | 41,227문장 재생 오류 0 | 실험 04, `CsvLogConverterTest` | 1회, 테스트로 고정 |
| `synchronous_commit=off`의 효과 | `END` 0.372ms → 0.023ms | 실험 04 | 1회 |
| 알람 기준 용량 탐색 (PostgreSQL) | 9.5, 10.0, 3.0, 13.0, 12.0배속. 3.0의 원인을 모름 | 실험 04·05 | 5회 |
| 부하 지표가 라운드마다 떠진다 (#2) | 두 기종에서 실행 중인 연결, 100ms 넘게 실행 중인 문장, CPU busy, Load Average | 실험 03·04, `MetricSamplerTest` | 실험마다 1회 |
| 100ms 넘게 실행 중인 문장이 과부하 라운드를 가른다 | MySQL 9개 라운드에서 버틴 쪽은 전부 0, 과부하 쪽은 전부 0이 아님. PostgreSQL은 8배속 라운드 하나가 예외 | 실험 03·04 | 1회 |
| Load Average(1분)는 3초짜리 라운드에 쓸 수 없다 | 버틴 9배속이 35, 과부하인 16배속이 6 | 실험 03 | 1회 |
| 전용 스레드 타이머의 깨우는 정밀도 | 중앙값 0.76ms → 0.03ms (도커 안) | 임시 측정, 스크립트는 남기지 않음 | 1회 |
| 타이머가 대기자를 빠뜨리지 않는다 | 400개 스레드, 80,000번 전부 깨어남 | `SpinTimerTest` | 테스트로 고정 |

## 확인하지 못한 것

- 네이티브 Linux와 운영급 장비에서의 수치
- 한 시간 넘는 녹화, 메모리에 안 들어가는 로그
- 복제 구성에서의 재생과 복제 지연
- 한 패킷에 여러 문장을 보내는 경우, `COPY`, `LOAD DATA`
- 녹화 전부터 autocommit이 꺼져 있던 연결
