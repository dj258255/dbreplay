# 실험 11: 주종 구성에서 함께 틀고 복제 지연을 본다

2026-10-12, MySQL 8.4(GTID 복제)와 PostgreSQL 16(스트리밍 복제), 도커, Apple Silicon 노트북 한 대. 이슈 #3.
1배속 재생은 조건마다 3번, 탐색도 조건마다 3번 했다.

메이투안 글은 주 DB의 SQL을 트랜잭션 단위로, 종 DB의 SQL을 하나씩 독립으로 함께 내보낸다. 재생 단위는 둘 다 있었지만
주종이 함께 있는 구성에서 돌려 본 적이 없었고, 복제 지연을 뜨지 못했다.

## 결론

- **MySQL에서는 복제 지연이 상한을 정했다.** 복제 지연 1초를 알람으로 걸자 주만 틀 때의 상한이 4.25, 5.00, 4.50배속이었다.
  과부하로 판정된 라운드 11개가 전부 복제 지연 때문이었다. 주 DB 한 대만 보던 실험들의 상한은 7.5~14배속이었다
  (실험 03, 같은 부하). 주 DB가 버티는 것과 종 DB가 따라오는 것은 다른 한계다.
- **배속을 올리면 복제 지연이 커진다(가설 1).** MySQL에서 주만 틀 때 지연의 최대가 1배속 0.0~0.2초, 4배속 0.3~0.5초,
  5배속 1.0~2.5초, 8배속 2.2~2.3초였다.
- **PostgreSQL에서는 복제 지연 알람이 한 번도 울리지 않았다.** 16배속까지 지연의 최대가 0.1초를 넘지 않았다. 부하를 건 채로
  직접 읽어 보면 `replay_lag`가 0.5~1ms다. 값이 안 읽힌 것이 아니라 지연이 그만큼 작다. 상한은 실행 중인 연결의 알람이 정했다.
- **함께 틀면 상한이 낮다(가설 2).** MySQL 3.75, 3.50, 2.75 대 4.25, 5.00, 4.50. PostgreSQL 7.00, 5.50, 1.88 대 12, 13, 13.
  두 기종 모두 세 번 다 낮았다. 다만 종 DB, 주 DB, 재생기가 한 장비의 CPU를 나눠 쓴다. 서버가 따로인 운영에서 같은 차이가
  날지는 이 실험이 말해 주지 않는다.
- **종 DB에 읽기를 함께 틀면 MySQL의 복제 지연이 커졌다.** 4배속에서 지연의 최대가 함께 1.7~2.1초, 주만 0.3~0.5초였다.

"한 번의 `explore`가 주와 종을 함께 다룰 것인가"(이슈 #3)는 함께 다루는 쪽으로 둔다. 따로 돌리면 이 차이를 볼 수 없다.

## 찾은 것

- **복제 스레드가 부하 지표에 섞였다.** 종 DB가 붙은 MySQL 주 DB에서 `slow_running`이 늘 1.0이었고 `active_sessions`가
  1 높았다. 종 DB에 바이너리 로그를 보내는 스레드가 "실행 중인 문장"으로 잡힌 것이다. 이 실험의 MySQL 수치는 그 상태로 잰 것이다.
  실험 뒤에 그 스레드를 빼도록 고쳤고, 한가한 주 DB에서 `slow_running`이 0으로 나오는 것을 확인했다.
- **`active_sessions`는 한가할 때도 1이다.** 복제가 없던 실험들에서도 그랬다(실험 03의 최솟값 1.00). 서버의 상주 스레드 하나가
  세어진다. 고치지 않았다. 알람 기준 32개가 실제로는 31개인 셈이다.
- **PostgreSQL에서 낮은 상한이 또 한 번 나왔다(1.88배속).** 2배속 라운드 하나에서 실행 중인 연결이 263개까지 치솟았고,
  그 아래의 1.5, 1.75, 1.88배속 라운드는 최대 2~3개로 조용했다. 부하가 높아서가 아니라 그 라운드에 무슨 일이 있었던 것으로 보인다.
  무엇인지는 모른다. 실험 04·05의 3.0, 실험 07의 3.25와 같은 종류로 보인다(#10).
- 맥의 도커에서 마운트한 초기화 스크립트가 실행 권한 오류로 돌지 않아 PostgreSQL 주 DB가 뜨지 못했다. 접속 규칙을 파일로 주게
  바꿨다. 그 사이 MySQL 부분은 끝나 있었고 PostgreSQL 부분만 다시 돌렸다(`./run.sh postgres`).

## 다시 돌리는 법

```sh
./run.sh                 # 두 기종. MySQL 약 20분, PostgreSQL 약 15분
./run.sh mysql           # 한 기종만
python3 summarize.py mysql   # out/의 출력을 아래의 표로 모은다 (mysql, pg)
docker compose down -v
```

## 한 일

1. 주종을 세운다. MySQL은 GTID 자동 위치로 복제를 걸고 종 DB를 `super_read_only`로 둔다. PostgreSQL의 종 DB는 처음 뜰 때
   `pg_basebackup -R`로 주 DB를 받아 스트리밍 복제로 붙는다.
2. 30초 동안 주 DB와 종 DB에 부하를 함께 걸고 두 서버의 로그를 따로 녹화해 따로 변환한다.

   | | 주 DB | 종 DB |
   |---|---|---|
   | MySQL | sysbench `oltp_read_write`, 초당 202 트랜잭션, 문장 121,142개 | `oltp_read_only`, 초당 197 트랜잭션, 문장 94,658개 |
   | PostgreSQL | pgbench 기본 트랜잭션, 초당 196, 문장 41,234개 | pgbench `-S`(조회만), 초당 1,507, 문장 45,215개 |

3. 되돌리기는 주 DB에 덤프를 되붓는 것이다. 종 DB는 그것을 복제로 받는다. 도구가 종 DB가 다 따라올 때까지 기다린 뒤 재생한다
   (MySQL은 GTID, PostgreSQL은 LSN).
4. 1배속으로 주만(`--replica-url`만 줌), 종만(종 DB에 문장 단위로), 함께(`--replica-trace`를 더함)를 번갈아 3번씩 튼다.
5. 함께 틀며 3번, 주만 틀며 3번 탐색한다. 알람은 `active_sessions>=32,replication_lag_seconds>=1`이다.

복제 지연은 `replication_lag_seconds`다. MySQL은 종 DB에서 적용 중인 트랜잭션이 주 DB에서 커밋된 시각과 지금의 차이를 읽는다.
PostgreSQL은 주 DB의 `pg_stat_replication.replay_lag`를 읽는다.

WAL을 그대로 받아 적용하고, MySQL의 종 DB는 트랜잭션을 다시 실행한다. 그 차이일 것으로 짐작하지만 확인하지 않았다.
쓰기의 양이 달라서는 아닌 것으로 보인다. 녹화의 초당 쓰기 문장이 MySQL 785, PostgreSQL 746으로 비슷하다.

## 한계

- 주 DB, 종 DB, 재생기가 한 장비에 있다. "함께 틀면 상한이 낮다"와 "읽기를 함께 틀면 지연이 커진다"는 CPU를 나눠 쓴 결과일 수 있다.
- MySQL의 지연 값은 두 서버의 시계가 같다는 것에 기댄다. 이 실험에서는 같은 장비라 같다. 종 DB가 바이너리 로그를 받는 것 자체가
  밀리는 경우(네트워크)는 이 값에 잡히지 않는다.
- 두 재생은 각자의 첫 문장을 기준으로 시각을 맞춘다. 주 DB의 문장과 종 DB의 문장 사이의 원래 간격은 지켜지지 않는다.
- 녹화가 30초다. 높은 배속의 라운드는 4초 안팎이라 지연이 다 벌어지기 전에 끝난다.
- 탐색은 조건마다 3번이다. PostgreSQL의 함께 트는 쪽은 7.00, 5.50, 1.88로 퍼졌다.
- 수위와 평가 파일은 주 DB의 트래픽만으로 계산한다. 종 DB의 것은 상한 배속을 곱한 값만 따로 보여 준다.
- 종 DB가 둘 이상인 구성, 반동기 복제, 논리 복제는 해 보지 않았다.
