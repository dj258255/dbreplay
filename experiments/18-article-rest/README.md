# 실험 18: 원문 대조에서 남은 것을 메운 것들이 실제 DB에서 도는가

2026-10-15, MySQL 8.4.11(GTID 복제)과 PostgreSQL 16(스트리밍 복제, `pg_stat_statements`), 도커, Apple Silicon 노트북. 상위 이슈 #90.

원문 대조표의 남은 줄을 메우면서(#79~#89), 단위 테스트가 통과한 뒤 실제 DB에서 한 번씩 돌려 본 기록이다. 실험 16과 같은 성격이다.
수치를 재는 실험이 아니라 기능이 도는지를 보는 확인이다. 묶음마다 스크립트 하나(`check-<이슈 번호>.sh`)와 출력(`out/*-result.txt`)이 있다.
패킷 캡처 녹화(#79)는 실험 19, 글의 사례(#89)는 실험 20이다.

## 다시 돌리는 법

```sh
./setup.sh && ./record.sh      # 주종 구성, 10초짜리 트래픽, 스냅샷
./check-83.sh                  # 각 묶음. 84와 88은 호스트에서 돈다(JDK 25, 도커)
docker compose down -v
```

## 예상과 다르게 나온 것

- **#87의 첫 확인은 기준 0.2에서 두 대상이 다 들었다.** sysbench의 `oltp_read_write`와 `oltp_read_only`는 SELECT 모양을 함께 쓰고 쓰기 문장(트랜잭션마다 20개 중 4개 안팎)만 다르다.
  거리가 0.20으로 기준의 경계였다. 규칙의 결함이 아니라 확인 조건을 경계에 잡은 것이다. 두 출력(`out/87-result-0.2.txt`, `out/87-result.txt`)을 다 남긴다.
- **#88의 설계는 커밋 전에 바뀌었다.** 처음에는 API가 JDBC URL과 계정을 요청에서 받았다. 커밋 전의 보안 검토가 짚었다(아무 주소로나 붙고 인증이 없다).
  대상 목록의 이름으로만 받고 토큰을 요구하게 바꿨다(#88의 코멘트).
- 첫 화면을 확인하는 줄이 "평가" 제목을 빠뜨린 것처럼 보였다. 출력을 걸러 낸 명령의 문제였고, 화면을 직접 받아 보니 있었다.

## 한계

- 묶음마다 한 번 돌렸다. 기능이 도는지를 본 것이고 수치를 잰 것이 아니다.
- #84는 호스트에 `mysql` 클라이언트가 없어 `--snapshot`(덤프 되붓기)을 여기서 돌리지 않았다. 되붓기는 `reset`과 같은 길이다(실험 05, 16).
- #81의 `--workers`가 재생기의 한계를 올리는지는 실험 20에서 본다. 여기서는 2배속까지만 돌렸다.
- #82의 PostgreSQL `slow_finished_total`은 서버 로그를 이 도구가 읽을 수 있는 자리에 둬야 한다. 운영에서 그 파일을 어떻게 가져올지는 다루지 않았다.
