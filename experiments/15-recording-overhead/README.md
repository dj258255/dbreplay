# 실험 15: 모든 문장을 서버 로그로 남기면 운영의 처리량이 얼마나 주는가

2026-10-14, MySQL 8.4.11과 PostgreSQL 16 (도커, Apple Silicon 노트북). 로그 끔과 켬을 번갈아 5번씩. 이슈 #51.

메이투안 글의 첫 목표는 재생과 평가가 운영 클러스터에 영향을 주지 않는 것이다. 글은 DB 커널에서 SQL을 수집한다.
이 도구는 운영 DB에서 모든 문장을 서버 로그로 남기게 한다. 그 부담을 한 번도 재지 않았다. 원문을 항목별로 다시 대조하다 찾았다
(`docs/verify/ARTICLE.md`의 3번).

## 결론

- **녹화는 공짜가 아니다.** 서버가 낼 수 있는 만큼 내는 상태에서 로그를 켜면 처리량이 MySQL에서 12%, PostgreSQL에서 16% 줄었다(중앙값).
  두 기종 모두 켬과 끔의 다섯 번이 겹치지 않는다. 가설(10% 이상 준다)은 맞았다.
- **지연도 는다.** MySQL의 p95가 7.8~8.4ms에서 8.7~13.5ms로, PostgreSQL의 평균이 1.37~1.57ms에서 1.66~1.87ms로.
- **로그는 초당 14~20MB로 쌓인다.** 한 시간이면 50~70GB다. 실험 01의 어림(초당 26,000문장에 한 시간 55GB)과 맞는다.
- 미리 적은 중단 규칙(20% 넘게 줄면 "운영에서 켜 두는 녹화"라는 전제가 깨진 것)에는 걸리지 않았다. 중앙값이 12%와 16%다.
  MySQL의 한 쌍은 23%였다.

이 도구는 글의 첫 목표를 채우지 못한다. 글은 커널에서 수집하고, 이 도구는 로그를 켜는 값을 치른다.
피크 시간에 30초에서 몇 분만 켜는 쓰임새라면 그동안 처리량의 10~20%를 내주는 셈이다.

## 이 수치를 읽을 때

- **포화 상태에서 잰 것이다.** 속도 제한 없이 8개 연결로 걸었다. 운영 DB가 여유 있게 돌고 있으면(수위 30~50%) 처리량은 줄지 않고
  지연과 CPU로 나타날 것이다. 그것은 재지 않았다.
- **로그를 DB와 같은 디스크에 썼다.** 운영에서 로그를 다른 디스크에 두면 달라질 수 있다.
- 노트북의 도커다. 디스크에 쓰는 비용이 실제 서버와 다르다.
- 같은 도커에 다른 프로젝트의 컨테이너 8개가 떠 있었다(시작 전 CPU 합계 약 5%). 끔과 켬은 같은 조건에서 번갈아 돌았다.

## 다시 돌리는 법

```sh
./run.sh                 # 약 12분
docker compose down -v
```

## 한 일

1. MySQL: sysbench `oltp_read_write`(테이블 4개, 10만 행), 8개 연결, 속도 제한 없음, 30초.
   `long_query_time=0`, `log_slow_extra=ON`인 채로 `slow_query_log`만 켜고 끈다. 이 도구가 요구하는 설정 그대로다.
2. PostgreSQL: pgbench 기본 트랜잭션(scale 5), 8개 연결, 30초. `log_min_duration_statement`를 -1과 0으로 바꾼다.
3. 20초 데운 뒤 끔, 켬, 끔, 켬 순으로 5번씩 돈다. 켬마다 로그 파일을 비우고 끝난 뒤의 크기를 잰다.

## 해 보지 않은 것

- 여유 있는 부하에서의 지연과 CPU.
- `log_slow_extra=OFF`. 로그는 줄지만 오류 번호와 읽은 행 수를 잃는다.
- 일부 연결만, 일부 문장만 남기는 방식(`log_slow_rate_limit` 같은 표본).
- 로그를 다른 디스크나 메모리 파일 시스템에 두는 경우.
- 녹화 전에 뜨는 덤프가 운영에 주는 부담.
