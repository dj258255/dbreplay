# 실험 20: 글의 사례를 도커 자원 제한으로 따라 한다

2026-10-17, MySQL 8.4 주 DB 하나와 종 DB 둘(GTID 복제), 도커, Apple Silicon 노트북(12코어). 이슈 #89, 원문 대조 45, 46a, 53a, 57.

글의 사례 셋(사양을 낮춘 뒤에도 요구를 채움, 서버 성능 비교, 위험한 클러스터의 확장)을 장비 하나에서 따라 한다. 도커의 자원 제한(`--cpus`)과
파라미터를 사양으로 본다. 서버가 따로인 운영과 같지 않다. 판정 기준은 재기 전에 #89에 적었다(10-17 착수 코멘트).

## 결론

- **1 사양 축소: 줄여도 요구를 채운다.** 주 DB의 CPU를 4에서 2로 줄이자 상한이 6.50~8.00에서 4.50~5.00배속이 됐다. 요구 배수 2를 넘는다.
  글의 사례(사양을 낮춘 뒤 6배 넘게 버텨 2배 요구를 채움)와 같은 모양이다.
- **2 서버 비교: 구분되지 않는다.** CPU 2에서 버퍼 풀 128MB는 3.75~4.75, 32MB는 2.75~3.75배속이었다. 범위가 3.75에서 닿는다.
  중앙값은 4.75 대 3.50으로 32MB가 낮지만, 같은 조건(CPU 2, 128MB)이 다시 띄우기 전에는 4.50~5.00, 다시 띄운 뒤에는 3.75~4.75였다.
  같은 조건끼리의 차이가 두 서버의 차이만큼 크다. 되풀이 3번으로는 이 정도의 차이를 가르지 못한다.
- **3 확장의 비례: 다시 재도 판정하지 못했다(#109).** 내장 알람으로 다시 재자(아래 "사례 3 다시 재기") 1대 1.88~2.75, 2대 3.25~8.00배속이었다.
  2대 ÷ 1대가 최소끼리 1.73배(1.6~2.4 안), 중앙값끼리 2.52배(밖)로 갈렸다. 2대가 1대의 1.7배 넘게 버틴다는 것은 분명하지만 퍼짐(79%)이 커서
  비례인지 그 이상인지 가르지 못한다. 처음 잰 것(바로 아래)은 알람이 울리지 않아 쓰지 못했다.
- **3 확장의 비례 (처음, `out/3-*`): 판정하지 못한다.** 재기 전 판정 규칙으로는 "맞지 않았다"(2대 ÷ 1대가 최소 1.00배, 중앙값 1.47배)가 나오지만 쓸 수 없다.
  탐색 여섯 번이 모두 "재생기가 내지 못해 대상의 한계를 보지 못했다"로 끝났고(재기 전에 정한 단서), 바깥 알람이 과부하에서 표본을 읽지 못해 울리지 않았다(아래).
  읽기 상한이 노드 수에 비례한다는 권고의 가정(#7)은 여전히 확인하지 않은 것이다.

## 다시 돌리는 법


## 한 일

1. 주 DB에서 sysbench 초당 200 트랜잭션으로 `oltp_read_write`와 `oltp_read_only`를 30초씩 녹화했다(문장 116,782개와 97,585개). 스냅샷을 떴다.
2. 사례 1, 2는 주 DB에서 `explore --repeat 3 --start-speed 1 --max-speed 32`, 알람 `active_sessions>=32`(내장, 연속 3).
   CPU는 `docker update --cpus`로 바꿨다. 버퍼 풀은 `SET PERSIST_ONLY`로 청크 크기와 함께 정하고 다시 띄웠다. 128MB도 같은 방식으로 다시 띄워 조건을 맞췄다.
3. 사례 3은 종 DB를 CPU 1씩으로 묶고, 읽기만 문장 단위로(`--only reads --workers 2`) 1대와 2대에 틀었다. 2대는 드라이버의 `loadbalance`로 나눴다.
   알람은 바깥 알람 체계 노릇을 하는 명령(`alarm-replicas.sh`)이다. 종 DB 가운데 하나라도 실행 중인 연결이 16개 이상인 표본이 세 번 연속이면 울린다.
4. 디스크 탐침(실험 21)을 함께 띄웠다. 탐색 동안 탐침이 8,180µs 이상인 때가 30초 넘게 이어지면 무효다. 무효는 없었다(가장 긴 이어짐 10초).

## 사례 3을 판정하지 못한 이유

**바깥 알람이 과부하에서 조용해졌다.** 기록기(`sample-replicas.sh`)는 0.2초마다 `mysql` 클라이언트로 새로 접속해 센다. 종 DB 1대 탐색에서
표본 1,035개 가운데 326개(31%)가 실패했다. 실패는 -1로 적혀 연속 횟수를 0으로 되돌린다. 그래서 1대 탐색의 4배속 라운드에서 도구가 잰 실행 중인 연결이
평균 91.6개(최대 601)였는데도 기록에서는 16개 이상이 두 번보다 길게 이어진 적이 없었다. 실패의 원인은 기록하지 않았다(오류를 버렸다).
도구는 이것을 #66에서 고쳤다(뜨지 못한 지표에 건 알람은 멈춘다). 실험이 만든 바깥 알람에는 그 장치가 없었다.

**왜곡은 재생기의 한계와 대상의 과부하를 가르지 못한다.** 문장 단위의 읽기만 재생에서 대상이 느려지면 재생기의 연결이 모두 대상에서 묶이고, 다음 문장이 늦게 나간다.
그것이 "재생기가 늦은 문장"으로 세어져 왜곡이 된다. 실험 07에서 재생기 자신의 한계는 제한 없는 대상에서 12배속 근처였다. 여기서는 CPU 1짜리 종 DB에서 4배속에 왜곡이 났다.
대상의 과부하였을 가능성이 크지만, 알람이 울리지 않아 이 실행으로는 가를 수 없다.

**드라이버의 분배를 시험 실행에서 고쳤다.** 처음 구성(`jdbc:mysql:loadbalance://종1,종2`)은 SELECT를 79,241 대 5,572로 한쪽에 몰았다. 드라이버가 연결을 맺을 때 한 번만 호스트를 고르고
자동 커밋에서는 다시 고르지 않는데, 녹화에서 무거운 연결이 sysbench의 8개뿐이다. `loadBalanceAutoCommitStatementThreshold=1`로 42,573 대 42,740이 됐다. 1대도 같은 경로로 걸었다.

**도구의 결함 하나를 함께 찾았다.** 여러 호스트의 URL로 지표를 뜨면 표본마다 다른 호스트를 읽는다. 2대 탐색의 `qps`가 초당 수백만으로 나왔다(서버마다의 누적값의 차이, #108).

## 돌리기 전에 고친 것

10-15에 준비한 스크립트를 돌리기 전에 검토해 고쳤다(#89의 착수 코멘트).
- `sb()`가 시험 이름을 두 번 넘겼다
- `SET GLOBAL innodb_buffer_pool_size`로 32MB를 주면 청크 크기(128MB)의 배수로 올라가 32MB가 되지 않는다
- 디스크 탐침과 무효 판정이 없었다

## 한계

- 사례마다 `--repeat 3` 한 번이다. 사례 2의 차이를 가를 횟수가 아니다
- 자원 제한은 한 장비의 CPU를 나눈 것이다. 주 DB, 종 DB 둘, 재생기가 같은 장비의 CPU 12개를 다툰다
- 사례 2의 "서버"는 버퍼 풀만 다른 같은 서버다. 글의 서버 성능 비교(다른 하드웨어)는 #12의 장비가 있어야 한다
- 사례 3은 판정하지 못했다(다시 재기는 #109). 다시 하려면 바깥 알람이 실패를 알리고(또는 도구의 지표로 알람을 걸고), 대상의 과부하와 재생기의 한계를 가를 지표가 있어야 한다

## 사례 3 다시 재기 (`run-109.sh`, #109, `out/109/`, 한 번)

처음 잰 것이 판정하지 못한 두 원인(바깥 알람이 과부하에서 조용해짐, 대상의 과부하가 재생기의 왜곡처럼 보임)을 도구의 내장 알람으로 피했다. 방법과 판정은 재기 전에 #109에 적었다.

- 녹화(`oltp_read_only` 30초)를 SELECT만 남기고 연결 단위로 두 반쪽으로 나눴다(`split.py`). 읽기 문장 83,721개, 반쪽 41,861과 41,860개, 무거운 연결 4개씩
- 1대: 전체를 종 DB 1에 `--only reads --workers 2`(재생기 둘), 알람 `active_sessions>=16`
- 2대: 반쪽 A를 종 DB 1에 `--only reads`, 반쪽 B를 `--replica-trace`로 종 DB 2에(재생기 하나씩), 알람 `active_sessions>=16,replica.active_sessions>=16`
- 종 DB는 CPU 1씩. 시험 실행(`out/109-smoke/`)에서 두 종 DB의 qps가 1,357과 1,364로 같은 몫을 받는 것을 봤다
