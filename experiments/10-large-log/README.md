# 실험 10: 메모리에 들어가지 않는 로그를 변환할 수 있는가

2026-10-12, Apple Silicon 노트북, JDK 25. 한 번 돌렸다. 이슈 #9.

변환기는 레코드를 전부 메모리에 올려 정렬했다. 초당 26,000문장이면 슬로우 로그가 한 시간에 약 55GB다(실험 01).
한 시간짜리 녹화를 변환하지 못했다. 외부 병합 정렬로 바꾸고, 힙을 1GB로 묶은 채 12GB짜리 로그를 변환해 봤다.

## 결론

- **바꾸기 전의 변환기는 78초 만에 메모리가 모자라 죽었다.** 바꾼 변환기는 같은 로그를 210초에 끝냈다.
  프로세스의 메모리(RSS)는 가장 클 때 0.68GB였다.
- **출력의 순서가 맞다.** 2,080만 줄 전부가 시작 시각 순이고, 연결마다 문장의 순번이 로그와 같았다. 어긋난 것 0개.
  문장 수, 연결 종료 수, 연결 수도 만든 것과 같았다.
- **메모리를 얼마로 잡든 출력이 같다.** 300MB 로그를 메모리에서 정렬한 출력과 8MB씩 25조각으로 나눠 정렬한 출력이
  바이트 단위로 같았다(`cmp`).

## 왜 외부 병합 정렬인가

서버 로그는 문장이 끝난 순서로 적히고 재생은 시작 순서가 필요하다. 선택지는 둘이었다.

| | 창 정렬 | 외부 병합 정렬 |
|---|---|---|
| 방식 | 정해진 시간 창 안에서만 순서를 다시 세우며 흘려 쓴다 | 조각마다 정렬해 임시 파일로 내리고 끝에 병합한다 |
| 순서 | 창보다 오래 걸린 문장이 있으면 틀어진다 | 언제나 맞다 |
| 메모리 | 창 길이 × 초당 문장 수 | 정한 만큼 |
| 디스크와 시간 | 더 쓰지 않는다 | 로그만큼의 임시 파일을 한 번 더 쓰고 읽는다 |

외부 병합 정렬을 골랐다. 기준은 틀린 순서를 허용하지 않는다는 것이다. 한 연결 안의 순서가 틀어지면 재생이 다른 일을
하게 되고 출력만 봐서는 알 수 없다.

이 실험의 로그에서 가장 긴 문장은 88.5초였고, 그 항목은 시작 순서로 있어야 할 자리보다 7,788,275항목 뒤에 적혀 있었다.
창 정렬이 이 로그를 맞게 세우려면 창에 780만 항목을 들고 있어야 한다. 그 길이를 미리 알 방법도 없다.
창 정렬은 구현하지 않았다. 이 계산으로만 비교했다.

## 다시 돌리는 법

```sh
export JAVA_HOME=<JDK 25의 경로>
./run.sh                                        # 디스크를 40GB쯤 쓴다
OLD=<예전 빌드의 bin/dbreplay> ./run.sh         # 바꾸기 전의 변환기도 함께 돌려 본다. 이렇게 돌려 약 7분이 걸렸다
BIG=60000000000 ./run.sh                        # 로그의 크기를 바꾼다 (바이트)
```

## 한 일

1. `GenerateSlowLog.java`로 MySQL 8.4의 슬로우 로그와 형식이 같은 가짜 로그를 만든다. 연결 64개가 `BEGIN`, 문장 1~8개,
   `COMMIT`을 되풀이하고, 서버가 그러듯 끝난 순서로 적는다. 50만 문장에 하나는 5~90초가 걸린다.
   경계가 아닌 문장에는 그 연결 안에서의 순번을 주석으로 단다.
2. 힙 1GB(`-Xmx1g`)로 변환한다. 메모리에 모으는 양의 기본값은 힙의 4분의 1이다.
3. `CheckTrace.java`로 출력을 한 줄씩 읽어 검사한다. 전체가 시작 시각 순인가, 연결마다 순번이 0부터 하나씩 느는가,
   `BEGIN`, 문장들, `COMMIT`의 차례가 지켜지는가, 끊긴 연결이 다시 나오지 않는가.

## 결과

| | 값 |
|---|---|
| 로그 | 12.0GB, 20,797,390항목, 로그의 길이 235초 (초당 88,683항목) |
| 1초 넘게 걸린 문장 | 25개, 가장 긴 것 88.5초 |
| 바꾸기 전의 변환기, 힙 1GB | 78초 뒤 `OutOfMemoryError` |
| 바꾼 변환기, 힙 1GB | 210초, 임시 파일 32개, RSS 최대 0.68GB |
| 트래픽 파일 | 3.8GB, 문장 20,795,804개, 연결 종료 1,586개, 연결 1,650개 |
| 검사 | 20,797,390줄, 어긋난 것 0개 |
| 끝난 뒤 남은 임시 폴더 | 0개 |

`out/`에 각 단계의 출력이 있다. 로그와 트래픽 파일은 지웠다.

## 한계

- 한 번 돌렸다. 걸린 시간은 이 노트북의 디스크에서 나온 값이다.
- 가짜 로그다. 문장이 짧고(60자 안팎) 모양이 네 가지뿐이다. 실제 서버의 큰 로그로는 해 보지 않았다.
  실제 서버의 로그 두 개(33KB, 193KB)로는 조각을 아주 작게 잡아 같은 출력이 나오는 것을 테스트로 확인했다.
- 55GB(한 시간 분량)로는 해 보지 않았다. 임시 파일이 한 번에 여는 수(64개)를 넘으면 여러 단계로 병합한다.
  그 경로는 테스트로만 확인했다.
- PostgreSQL의 큰 로그로는 해 보지 않았다. 같은 버퍼를 쓴다.
- 연결 수만큼의 메모리는 여전히 쓴다. 짧게 맺고 끊는 연결이 수백만 개인 로그에서는 그것이 한도가 될 수 있다.
- 재생기와 비교, 탐색이 큰 트래픽 파일에서 어떻게 도는지는 이 실험의 범위가 아니다.
