# 실험 03: 변경 전후 비교와 용량 탐색 (MySQL)

2026-10-11, MySQL 8.4.11 (도커, Apple Silicon 노트북). 재생기는 Java 25, Connector/J 9.4.0.

메이투안 글의 흐름을 한 번에 돌렸다. 변경 전과 변경 후의 샌드박스에 같은 트래픽을 트랜잭션 단위로 틀어 SQL
모양별로 비교하고(트래픽 재생), 각각에서 알람이 울리는 배속을 찾고(용량 탐색), 수위를 내고(용량 운영), 평가가
아직 유효한지 확인했다. 변경은 글의 사례와 같은 테이블 압축이다.

## 결론

- **테이블 압축의 비용이 SQL 모양 단위로 나왔다.** `INSERT`가 6.5배, `UPDATE`가 3.9배, 한 행 조회가 2배가 됐다.
- **저장 공간은 69%가 됐다.** 테이블 하나가 32MB에서 22MB로 줄었다.
- **알람 없이 버틴 배속이 8.50에서 3.75로 내려갔다.** 상한이 초당 33,450문장에서 14,758문장으로 줄었다.
- **수위는 12%에서 27%가 됐다.** 건강 구간(30~50%)의 아래라 둘 다 과잉이다.
- **상한의 절대값은 실행마다 흔들렸다.** 같은 절차를 한 번 더 돌렸을 때는 7.50과 2.75였다. 압축이 상한을 절반
  아래로 낮춘다는 방향은 두 번 다 같았다.

메이투안 글의 사례는 가장 많이 실행되는 SQL이 0.90ms에서 0.97ms로, 저장 공간이 40%로였다. 여기서는 비용이 더
크고 절약이 더 작다. sysbench의 데이터가 무작위 문자열이라 잘 눌리지 않고, 문장이 짧아 압축을 푸는 시간의
비중이 크다.

## 다시 돌리는 법

```sh
./run.sh                 # 약 14분
docker compose down -v
```

녹화 조건은 `oltp_read_write`, 테이블 4개에 10만 행씩, 스레드 8개, 초당 200트랜잭션, 30초다.
변경은 `reset-compressed.sh`가 넣는다. 되돌린 뒤 네 테이블에 `ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8`을 건다.

## 글의 방식과 맞춘 것

| 글 | 이 실험 |
|---|---|
| 주 DB의 SQL을 트랜잭션 단위로 묶어 내보냄 | `--unit transaction` (기본값). 트랜잭션마다 계획 시각에 풀의 연결을 가져다 쓴다 |
| 종 DB의 SQL을 하나씩 독립으로 내보냄 | `--unit statement`. 끝에서 한 번 돌렸다 |
| 사용자가 건 알람이 울리면 과부하 | 알람 둘을 걸었다. 아래 "알람" 참고 |
| 지수로 올린 뒤 이분으로 좁힘 | 두 배씩 올리고, 버틴 배속과 못 버틴 배속의 차이가 10% 이하가 될 때까지 좁혔다 |
| 라운드마다 데이터를 되돌림 | `--reset-command`가 덤프를 되붓고 통계를 다시 잡는다 |
| 수위 = 운영 QPS ÷ 상한 QPS, 건강 구간 30~50% | 그대로 |
| 평가에 유효 기간, 조건이 바뀌면 무효 | `--out`으로 평가를 남기고 `dbreplay check`로 확인했다 |

## 알람

글은 과부하를 사용자가 클러스터에 건 알람으로 판정하고, 알람의 항목과 임계값은 밝히지 않았다. 이 실험에서는
둘을 걸었다. 값은 실험을 위해 고른 것이다.

- **내장 알람**: 대상에서 실행 중인 연결이 32개 이상인 채로 0.2초 간격 표본에 3번 연속 잡히면 울린다.
- **알람 확인 명령** (`alarm-slow.sh`): 그 라운드에 100ms 넘게 걸린 문장이 50개 이상이면 울린다.
  서버의 `performance_schema.events_statements_histogram_global`에서 센다.

## 변경 전 대 변경 후 (1배속)

재생할 때마다 샌드박스의 슬로우 로그를 켜고, 그 로그를 변환한 파일 둘을 비교했다. 원자료는
`out/compare-before-vs-after.txt`에 있다.

| SQL 모양 | 횟수 | 평균 (전 → 후) | 변화 |
|---|---|---|---|
| `INSERT INTO sbtest1 (id, k, c, pad) VALUES (?+)` | 1,476 | 0.063ms → 0.407ms | +551.2% |
| `UPDATE sbtest1 SET k=k+? WHERE id=?` | 1,532 | 0.130ms → 0.505ms | +288.5% |
| `SELECT c FROM sbtest1 WHERE id=?` | 15,200 | 0.046ms → 0.090ms | +97.1% |
| `COMMIT` | 6,035 | 3.705ms → 3.219ms | -13.1% |

전체로는 평균 0.252ms → 0.311ms, 중앙값 0.045ms → 0.056ms, p99 2.944ms → 3.584ms다. 실패는 양쪽 다 없다.

## 원본 대 변경 전 재생

| 항목 | 원본 | 재생 |
|---|---|---|
| 문장 수 | 120,702 | 120,870 |
| 실행 시간 평균 | 0.141ms | 0.252ms |
| 실행 시간 중앙값 | 0.038ms | 0.045ms |
| `COMMIT` 평균 | 1.788ms | 3.705ms |

재생 쪽의 `COMMIT`이 두 배다. 재생은 덤프를 되부은 직후에 시작해서 서버가 그 쓰기를 디스크에 내리는 중이었다.
서버 로그에 리두 로그의 체크포인트가 밀린다는 경고가 남아 있었다. 되돌린 뒤 서버가 조용해질 때까지 기다리는
단계가 없다. 변경 전과 변경 후는 둘 다 같은 조건이라 서로의 비교에는 영향이 작다.

한 행 조회는 0.032ms에서 0.046ms로 길다. 원본은 준비된 문장을 바이너리 프로토콜로 실행했고 재생은 문장마다
텍스트를 보내 파싱한다.

없다.

## 실행마다의 흔들림

같은 스크립트를 앞서 한 번 돌렸을 때의 결과다. 그때의 출력 파일은 남기지 않았다.

| | 앞선 실행 | 이번 실행 |
|---|---|---|
| 변경 전 상한 배속 | 7.50 | 8.50 |
| 변경 후 상한 배속 | 2.75 | 3.75 |
| 변경 전 수위 | 13% | 12% |
| 변경 후 수위 | 36% (적정) | 27% (과잉) |

변경 후의 수위 판정이 실행에 따라 적정과 과잉으로 갈렸다. 30초짜리 녹화와 3~10초짜리 라운드로는 상한이 이만큼
흔들린다. 판정에 쓰려면 녹화를 길게 잡고 여러 번 돌려야 한다.

## 문장 단위 재생

`--unit statement`로 한 번 틀었다 (`out/replay-statement.txt`).

| 항목 | 값 |
|---|---|
| 실행한 문장 / 건너뛴 문장 | 108,631 / 12,071 |
| 쓴 연결 수 | 148 |
| 늦은 정도 (중앙값 / p99) | 0.022ms / 1.152ms |
| 재생 오류 | 244 |

건너뛴 것은 `BEGIN`과 `COMMIT`이다. 오류 244개는 쓰기 문장의 순서가 바뀌어 생긴 것이다. 원본에서는 한
트랜잭션 안에서 `DELETE` 뒤에 같은 키의 `INSERT`가 왔는데, 독립으로 내보내면 `INSERT`가 먼저 도착할 수 있다.
글이 이 방식을 종 DB의 읽기에만 쓰는 이유다.

## 평가의 유효성

`explore --out`이 남긴 평가를 `dbreplay check`로 확인했다.

- 아무것도 바꾸지 않았을 때: 유효하다 (`out/check-valid.txt`).
- `innodb_io_capacity`를 바꾸고 알람 임계값을 64로 올려 물었을 때: 무효다. 두 이유가 각각 나왔다
  (`out/check-invalid.txt`).

글이 든 무효 조건 넷 가운데 버전·파라미터, 알람 임계값, 트래픽 모양은 확인한다. 하드웨어 사양은 DB 접속으로
알 수 없어 확인하지 못한다. 유효 기간의 기본값 30일은 글에 없는 값이다.

## 앞선 방식과의 차이

이 실험은 처음에 연결 단위로 재생하고 재생기가 잰 값(시간 초과 5% 등)으로 과부하를 판정했다. 그때의 상한은
5.00과 4.25였다 (`out/session-unit-run/`). 그 기준은 글에 없는 것이어서 알람으로 바꿨다.

그 과정에서 찾아 고친 것이 둘 있다.

- Connector/J가 쓰기 문장마다 `SELECT @@session.transaction_read_only`를 먼저 보냈다. 원본 118,822문장에
  23,764번이 더 나갔다. 재생기가 `useLocalSessionState=true`를 기본으로 넣는다.
- 운영체제 타이머에 맡기면 가상 스레드가 계획 시각보다 중앙값 0.76ms 늦게 깨어났다. 전용 스레드가 돌면서
  깨우게 바꿔 0.03ms가 됐다. 재생하는 동안 코어 하나를 쓴다.

## 한계

- 원본과 대상이 같은 서버이고 노트북이다.
- 변경 전과 변경 후의 1배속 비교는 한 번씩만 돌렸다.
- 알람의 임계값(실행 중 32개, 100ms 넘는 문장 50개)과 표본 간격은 30초짜리 녹화에 맞춰 고른 것이다.
- 되돌린 직후 서버가 조용해지기를 기다리지 않는다.
- CPU와 Load Average, 복제 지연은 뜨지 않는다. 그런 알람은 알람 확인 명령으로 넣어야 한다.
