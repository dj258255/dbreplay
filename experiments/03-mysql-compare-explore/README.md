# 실험 03: 변경 전후 비교와 용량 탐색 (MySQL)

2026-10-11, MySQL 8.4.11 (도커, Apple Silicon 노트북). 재생기는 Java 25, Connector/J 9.4.0.

메이투안 글의 흐름을 한 번에 돌렸다. 변경 전과 변경 후의 샌드박스에 같은 트래픽을 트랜잭션 단위로 틀어 SQL
모양별로 비교하고(트래픽 재생), 각각에서 알람이 울리는 배속을 찾고(용량 탐색), 수위를 내고(용량 운영), 평가가
아직 유효한지 확인했다. 변경은 글의 사례와 같은 테이블 압축이다.

## 결론

- **테이블 압축의 비용이 SQL 모양 단위로 나왔다.** `INSERT`가 6.1배, `UPDATE`가 4.6배, 한 행 조회가 2배가 됐다.
- **저장 공간은 69%가 됐다.** 테이블 하나가 32MB에서 22MB로 줄었다.
- **알람 없이 버틴 배속은 압축 뒤에 일곱 번 모두 내려갔다.** 압축 전 7.50~14.00, 압축 후 1.88~6.00이었다.
  내려간 정도는 실행마다 달라서 압축 후가 압축 전의 0.19배에서 0.67배까지였다.
- **상한의 절대값은 실행마다 흔들려서 수위 판정이 갈렸다.** 압축 후의 수위가 17%에서 53%까지 나와 판정이
  과잉 다섯, 적정 하나, 부족 하나였다. 30초 녹화 한 번으로는 판정할 수 없다(#10).
- **부하 지표가 라운드마다 떠진다.** 압축 전 1배속에서 평균 17%이던 CPU busy가 8배속에서 53%가 됐다.

메이투안 글의 사례는 가장 많이 실행되는 SQL이 0.90ms에서 0.97ms로, 저장 공간이 40%로였다. 여기서는 비용이 더
크고 절약이 더 작다. sysbench의 데이터가 무작위 문자열이라 잘 눌리지 않고, 문장이 짧아 압축을 푸는 시간의
비중이 크다.

아래의 상세 수치는 네 번째 실행의 것이다. 그 실행의 탐색 출력은 `out/fourth-run/`에 있고 나머지 출력은 남기지 않았다.
`out/`에 있는 파일은 일곱 번째 실행의 것이다. 다섯 번째부터는 되돌리기를 스크립트에서 도구의 옵션으로 바꾼 뒤에 돌렸다(#4).
일곱 번째 실행의 변경 전후 비교를 문서 하나로 낸 것이 [`report-example.md`](report-example.md)다(#5).
실행마다의 상한은 "실행마다의 흔들림"에 모았다.

## 다시 돌리는 법

```sh
./run.sh                 # 약 15분
docker compose down -v
```

녹화 조건은 `oltp_read_write`, 테이블 4개에 10만 행씩, 스레드 8개, 초당 200트랜잭션, 30초다.
되돌리기는 도구가 한다. 덤프를 되붓고, 변경을 넣고, 통계를 다시 잡고, 서버가 조용해질 때까지 기다린다(실험 05).
변경은 `--change-command`로 넘긴 `compress.sh`가 넣는다. 네 테이블에 `ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8`을 건다.
되돌리는 데 6.6초, 압축까지 넣으면 9.5초가 걸렸다.

## 글의 방식과 맞춘 것

| 글 | 이 실험 |
|---|---|
| 주 DB의 SQL을 트랜잭션 단위로 묶어 내보냄 | `--unit transaction` (기본값). 트랜잭션마다 계획 시각에 풀의 연결을 가져다 쓴다 |
| 종 DB의 SQL을 하나씩 독립으로 내보냄 | `--unit statement`. 끝에서 한 번 돌렸다 |
| 사용자가 건 알람이 울리면 과부하 | 알람 둘을 걸었다. 아래 "알람" 참고 |
| 지수로 올린 뒤 이분으로 좁힘 | 두 배씩 올리고, 버틴 배속과 못 버틴 배속의 차이가 10% 이하가 될 때까지 좁혔다 |
| 백업으로 녹화 시작 시점의 스냅샷을 만들고 라운드마다 되돌림 | `--snapshot`으로 덤프를 주면 도구가 되붓고, 통계를 다시 잡고, 기다린다 |
| 재생 전의 변경 창 | `--change-command` |
| 수위 = 운영 QPS ÷ 상한 QPS, 건강 구간 30~50% | 그대로 |
| 평가에 유효 기간, 조건이 바뀌면 무효 | `--out`으로 평가를 남기고 `dbreplay check`로 확인했다 |

## 알람

글은 과부하를 사용자가 클러스터에 건 알람으로 판정하고, 알람의 항목과 임계값은 밝히지 않았다. 이 실험에서는
둘을 걸었다. 값은 실험을 위해 고른 것이다.

- **지표 알람** (`--alarm-metric "active_sessions>=32"`): 대상에서 실행 중인 연결이 32개 이상인 채로 0.2초 간격
  표본에 3번 연속 잡히면 울린다.
- **알람 확인 명령** (`alarm-slow.sh`): 그 라운드에 100ms 넘게 걸린 문장이 50개 이상이면 울린다.
  서버의 `performance_schema.events_statements_histogram_global`에서 센다.

## 변경 전 대 변경 후 (1배속)

재생할 때마다 샌드박스의 슬로우 로그를 켜고, 그 로그를 변환한 파일 둘을 비교했다. 원자료는
`out/compare-before-vs-after.txt`에 있다.

| SQL 모양 | 횟수 | 평균 (전 → 후) | 변화 |
|---|---|---|---|
| `INSERT INTO sbtest1 (id, k, c, pad) VALUES (?+)` | 1,514 | 0.051ms → 0.313ms | +514.9% |
| `UPDATE sbtest1 SET k=k+? WHERE id=?` | 1,500 | 0.087ms → 0.397ms | +355.7% |
| `SELECT c FROM sbtest1 WHERE id=?` | 14,820 | 0.031ms → 0.063ms | +102.2% |
| `COMMIT` | 6,009 | 1.405ms → 1.823ms | +29.8% |

전체로는 평균 0.116ms → 0.212ms, 중앙값 0.036ms → 0.048ms, p99 1.728ms → 2.496ms다. 실패는 양쪽 다 없고
좋아진 모양도 없다.

이 비교는 네 번 했다. 연결 단위로 재생한 앞선 실행(`out/session-unit-run/`)과 트랜잭션 단위의 세 실행이다.
`INSERT`는 +614%, +551%, +515%, +556%, 한 행 조회는 +104%, +97%, +102%, +125%로 나왔다. 방향과 크기가 실행마다 비슷하다.
`COMMIT`은 +18%, -13%, +30%, +40%로 부호가 갈려서 변경의 효과라고 말할 수 없다.

1배속 재생 동안의 부하 지표는 이렇다(`out/replay-before.txt`, `out/replay-after.txt`).

| | 실행 중인 연결 (평균 / 최대) | CPU busy (평균 / 최대) | 100ms 넘게 실행 중인 문장 |
|---|---|---|---|
| 녹화 (운영 쪽) | 1.56 / 8 | 4.5% / 5.8% | 0 |
| 변경 전 재생 | 1.47 / 5 | 17.3% / 27.0% | 0 |
| 변경 후 재생 | 1.63 / 5 | 19.3% / 33.5% | 0 |

녹화 때의 4.5%와 재생 때의 17%의 차이는 대부분 재생기다. 재생기의 타이머 스레드가 코어 하나를 계속 쓰고,
이 값은 DB와 재생기가 함께 있는 장비 전체의 CPU다. 변경 전과 변경 후의 차이 2%p가 압축의 CPU 비용에 해당한다.

## 원본 대 변경 전 재생

| 항목 | 원본 | 재생 |
|---|---|---|
| 문장 수 | 120,333 | 120,551 |
| 실행 시간 평균 | 0.119ms | 0.116ms |
| 실행 시간 중앙값 | 0.032ms | 0.036ms |
| 실행 시간 p99 | 1.984ms | 1.728ms |
| `COMMIT` 평균 | 1.531ms | 1.405ms |

한 행 조회는 0.024ms에서 0.031ms로 30% 길다. 원본은 준비된 문장을 바이너리 프로토콜로 실행했고 재생은 문장마다
텍스트를 보내 파싱한다.

앞선 실행에서는 재생 쪽의 `COMMIT`이 원본의 두 배(1.788ms → 3.705ms)로 나온 적이 있다. 덤프를 되부은 직후라
서버가 그 쓰기를 디스크에 내리는 중이었고, 서버 로그에 리두 로그의 체크포인트가 밀린다는 경고가 남아 있었다.
이번 실행에서는 그렇지 않았다. 되돌린 뒤 서버가 조용해질 때까지 기다리는 단계가 없어서 실행마다 다르다(#4).

## 부하 지표

재생하는 동안 0.2초마다 DB에서 두 지표를, 1초마다 지표 명령(`metrics.sh`)으로 두 지표를 떴다.
칸의 값은 그 라운드의 평균 / 최대다. 변경 전의 탐색이다.

| 배속 | 판정 | 실행 중인 연결 | 100ms 넘게 실행 중인 문장 | CPU busy (%) | Load Average (1분) |
|---|---|---|---|---|---|
| 1 | 버팀 | 1.4 / 4 | 0 / 0 | 17.1 / 26.7 | 5.6 / 5.8 |
| 2 | 버팀 | 1.7 / 7 | 0 / 0 | 21.8 / 26.7 | 6.2 / 6.4 |
| 4 | 버팀 | 2.8 / 7 | 0 / 0 | 34.1 / 43.5 | 6.5 / 6.7 |
| 8 | 버팀 | 10.2 / 63 | 0 / 0 | 52.7 / 66.1 | 6.7 / 6.8 |
| 9 | 버팀 | 10.7 / 31 | 0 / 0 | 51.0 / 64.9 | 35.4 / 36.0 |
| 9.5 | 과부하 | 53.6 / 297 | 3.2 / 67 | 52.0 / 70.6 | 32.6 / 32.8 |
| 10 | 과부하 | 158.5 / 487 | 18.6 / 238 | 55.6 / 80.9 | 13.8 / 13.8 |
| 12 | 과부하 | 84.2 / 395 | 5.1 / 85 | 55.0 / 79.6 | 12.9 / 14.4 |
| 16 | 과부하 | 190.4 / 458 | 20.9 / 289 | 57.4 / 84.0 | 6.3 / 6.3 |

읽은 것은 이렇다.

- **CPU busy는 8배속까지 배속을 따라 오르고 그 위에서는 55% 근처에서 멈춘다.** 과부하 라운드에서도 CPU가 남는다.
  이 구성에서 먼저 막히는 것은 CPU가 아니다. 무엇이 막는지는 이 지표들로는 알 수 없다.
- **100ms 넘게 실행 중인 문장은 버틴 라운드에서 전부 0이고 과부하 라운드에서 전부 0이 아니다.** 이 실험에서는
  알람 확인 명령의 판정과 정확히 같은 선을 그었다.
- **Load Average(1분)는 이 길이의 라운드에 쓸 수 없다.** 3초짜리 라운드의 값이 앞 라운드와 그 사이의 되돌리기에서
  온다. 9배속(버팀)이 35이고 16배속(과부하)이 6이다.
- **CPU busy와 Load Average는 장비 전체의 값이다.** DB와 재생기가 같은 장비에 있어 재생기의 CPU가 섞여 있다.

## 실행마다의 흔들림

같은 절차를 일곱 번 돌렸다. 첫 두 번과 다섯 번째의 출력 파일은 남기지 않았고, 세 번째, 네 번째, 여섯 번째의 탐색 출력은
`out/third-run/`, `out/fourth-run/`, `out/sixth-run/`에, 일곱 번째는 `out/`에 있다. 다섯 번째부터는 되돌리기를 도구가 했다.

| 실행 | 변경 전 상한 | 변경 후 상한 | 변경 후 ÷ 변경 전 | 변경 후 수위와 판정 |
|---|---|---|---|---|
| 1 | 7.50 | 2.75 | 0.37 | 36%, 적정 |
| 2 | 8.50 | 3.75 | 0.44 | 27%, 과잉 |
| 3 | 10.00 | 1.88 | 0.19 | 53%, 부족 |
| 4 | 9.00 | 3.50 | 0.39 | 29%, 과잉 |
| 5 | 7.50 | 5.00 | 0.67 | 20%, 과잉 |
| 6 | 14.00 | 6.00 | 0.43 | 17%, 과잉 |
| 7 | 11.00 | 3.75 | 0.34 | 27%, 과잉 |

변경 전 상한은 7.50에서 14.00까지, 변경 후 상한은 1.88에서 6.00까지 흔들렸다. 압축이 상한을 낮춘다는 것은 일곱 번 다
같았다. 얼마나 낮추는지는 0.19배에서 0.67배까지 갈렸고, 네 번째까지 보고 적었던 "절반 아래"는 다섯 번째에서 깨졌다.
수위 판정은 과잉 다섯, 적정 하나, 부족 하나다.

세 번째 실행의 변경 후 탐색은 1배속 라운드에서 Load Average가 15.8로 시작했다. 앞의 탐색이 남긴 부하가 가라앉기
전이었다. 라운드 사이와 탐색 사이에 장비가 조용해지기를 기다리지 않는 것이 흔들림의 한 원인으로 보이지만 확인하지
않았다. 녹화 길이, 반복 횟수, 대기 시간을 바꿔 가며 재는 일은 #10에 있다.

| 5 | 106,477 / 11,816 | 160 | 0.76% | 283 |

건너뛴 것은 `BEGIN`과 `COMMIT`이다. 오류는 쓰기 문장의 순서가 바뀌어 생긴 것이다. 원본에서는 한 트랜잭션 안에서
`DELETE` 뒤에 같은 키의 `INSERT`가 왔는데, 독립으로 내보내면 `INSERT`가 먼저 도착할 수 있다. 글이 이 방식을
종 DB의 읽기에만 쓰는 이유다.

첫 실행에서 연결이 상한까지 열린 것을 보고 시작 전에 연결 16개를 미리 열게 고쳤다. 그 뒤 두 번은 106개와 148개였다.
네 번째 실행에서는 다시 상한을 넘겨 열렸고 오류도 두 배다. 이 재생은 두 번의 용량 탐색 바로 뒤에 돌아서
장비의 Load Average가 10을 넘는 상태였다.

## 평가의 유효성

`explore --out`이 남긴 평가를 `dbreplay check`로 확인했다.

- 아무것도 바꾸지 않았을 때: 유효하다 (`out/check-valid.txt`).
- `innodb_io_capacity`를 바꾸고 알람 임계값을 64로 올려 물었을 때: 무효다. 두 이유가 각각 나왔다
  (`out/check-invalid.txt`).

글이 든 무효 조건 넷 가운데 버전·파라미터, 알람 임계값, 트래픽 모양은 확인한다. 하드웨어 사양은 DB 접속으로
알 수 없어 확인하지 못한다. 유효 기간의 기본값 30일은 글에 없는 값이다.

## 앞선 방식과의 차이

이 실험은 처음에 연결 단위로 재생하고 재생기가 잰 값(시간 초과 5% 등)으로 과부하를 판정했다. 그때의 상한은
5.00과 4.25였다 (`out/session-unit-run/`). 그 기준은 글에 없는 것이어서 알람으로 바꿨다.

그 과정에서 찾아 고친 것이 둘 있다.

- Connector/J가 쓰기 문장마다 `SELECT @@session.transaction_read_only`를 먼저 보냈다. 원본 118,822문장에
  23,764번이 더 나갔다. 재생기가 `useLocalSessionState=true`를 기본으로 넣는다.
- 운영체제 타이머에 맡기면 가상 스레드가 계획 시각보다 중앙값 0.76ms 늦게 깨어났다. 전용 스레드가 돌면서
  깨우게 바꿔 0.03ms가 됐다. 재생하는 동안 코어 하나를 쓴다.

## 한계

- 원본과 대상이 같은 서버이고 노트북이다.
- 변경 전과 변경 후의 1배속 비교는 실행마다 한 번씩이다. 세 번의 실행에서 방향이 같았던 모양만 결론에 적었다.
- 알람의 임계값(실행 중 32개, 100ms 넘는 문장 50개)과 표본 간격은 30초짜리 녹화에 맞춰 고른 것이다.
- 되돌린 뒤 기다리는 단계가 수치를 가라앉히는지는 확인하지 못했다(실험 05).
- 복제 지연은 뜨지 않는다. 주종 구성이 없다(#3).
- 지표 명령을 1초마다 실행한다. 그 명령이 0.2초를 자면서 CPU를 재므로 CPU busy의 표본은 1초 중 0.2초만 본다.
