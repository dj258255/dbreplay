# 실험 02: 재생이 원본과 얼마나 같은가

2026-10-11, MySQL 8.4.11 (도커, Apple Silicon 노트북). 재생기는 Java 25.0.4, Connector/J 9.4.0.

sysbench 부하를 슬로우 로그로 녹화하고, 데이터를 녹화 시작 시점으로 되돌린 뒤 같은 서버에 배속을 바꿔 가며
다시 틀었다.

## 결론

- **2배속까지는 원본과 거의 같게 나간다.** 초 단위 문장 수의 차이가 평균 0.2~0.3%, 최대 0.9%다.
- **4배속부터 어긋나고 8배속에서 포화한다.** 포화 처리량은 초당 약 18,700문장이다.
- **재생 오류는 0개다.** 원본도 0개였다. 문장 120,122개가 전부 성공했다.
- **문장 하나하나는 1배속에서도 계획보다 늦다.** 중앙값 1.6ms다. 원인은 재생의 왕복 시간이 원본보다 긴 것이다.
- **도구가 실험 절차의 결함을 잡았다.** 되돌린 직후 통계가 틀어져 한 테이블의 범위 조회가 풀 스캔으로
  바뀌었는데, SQL 모양별 비교에서 바로 드러났다.

## 다시 돌리는 법

```sh
./run.sh                                   # 녹화, 변환, 호스트에서 1·2·4·8배속 재생
(cd ../.. && ./gradlew installDist)
for s in 1 2 4 8 16; do ./replay-in-network.sh $s; done
docker compose down -v
```

녹화 조건은 `oltp_read_write`, 테이블 4개에 10만 행씩, 스레드 8개, 초당 200트랜잭션으로 제한, 30초다.
원본은 6,006트랜잭션, 120,120문장이었다.

## 배속별 결과

재생기를 DB와 같은 도커 네트워크 안에서 돌린 값이다. 원자료는 `out/replay-net-*.txt`에 있다.

| 배속 | 계획 시간 | 실제 시간 | 초별 문장 수 차이 (평균 / 최대) | 늦은 정도 (중앙값 / p99) |
|---|---|---|---|---|
| 1 | 30.61초 | 30.62초 | 0.18% / 0.50% | 1.57ms / 8.53ms |
| 2 | 15.31초 | 15.31초 | 0.33% / 0.90% | 1.82ms / 8.86ms |
| 4 | 7.65초 | 7.65초 | 5.66% / 25.25% | 4.15ms / 84.41ms |
| 8 | 3.83초 | 6.41초 | 39.25% / 62.51% | 1,334.78ms / 2,596.42ms |
| 16 | 1.91초 | 6.61초 | 72.68% / 91.34% | 2,379.66ms / 4,637.93ms |

"초별 문장 수 차이"는 원본의 1초 구간마다 원본에서 시작된 문장 수와 재생에서 나간 문장 수를 비교한 것이다.
처음과 마지막 1초는 뺐다.

## 발견 1: 되돌린 직후의 통계가 실행 계획을 바꿨다

처음에는 1배속에서도 재생이 원본을 따라가지 못했다. 문장의 늦은 정도가 중앙값 3.2초였다.

SQL 모양별로 원본과 재생의 중앙값을 나란히 놓으니 한 테이블만 달랐다.

| SQL 모양 | 원본 중앙값 | 재생 중앙값 |
|---|---|---|
| `SELECT c FROM sbtest1 WHERE id BETWEEN ? AND ?` | 59µs | 16,792µs |
| `SELECT c FROM sbtest4 WHERE id BETWEEN ? AND ?` | 59µs | 346µs |

덤프를 되부은 직후의 `mysql.innodb_table_stats`에 `sbtest1`의 행 수가 46으로 남아 있었다. 실제는 10만 행이다.
옵티마이저가 범위 조회에 풀 스캔(`type: ALL`)을 골랐고, `ANALYZE TABLE` 뒤에는 `range`로 돌아왔다.

`reset.sh`가 되돌린 뒤 `ANALYZE TABLE`을 돌리게 고쳤다. 위 표는 고친 뒤의 값이다.
고치기 전의 요약은 `out/replay-host-stale-stats-*.txt`에 남겼다.

## 발견 2: 재생기는 DB 옆에서 돌려야 한다

| 재생기 위치 | 문장 실행 시간 중앙값 | 늦은 정도 중앙값 |
|---|---|---|
| 호스트 (도커 포트 포워딩 경유) | 0.592ms | 5.63ms |
| DB와 같은 도커 네트워크 | 0.168ms | 1.57ms |

1배속의 전체 시간은 두 경우 모두 계획과 같았다(30.62초).

## 발견 3: 문장 단위로는 1배속에서도 늦는다

원본에서 한 연결의 문장 사이 간격은 중앙값 45µs였고 서버 실행 시간은 중앙값 31µs였다. 문장 하나의 왕복이
75µs쯤이다. 재생에서는 문장 하나가 중앙값 168µs 걸렸다. 그래서 트랜잭션 안에서 문장이 뒤로 갈수록 밀리고,
트랜잭션 사이의 빈 시간에 따라잡는다.

차이의 원인은 나눠 재지 않았다. 후보는 원본이 바이너리 프로토콜의 준비된 문장을 쓴 것(재생은 문장마다
텍스트를 파싱한다), JDBC 드라이버와 가상 스레드의 깨어나는 비용, JIT 예열이다.

## 발견 4: 원본과 재생의 실행 시간은 같은 자로 잰 값이 아니다

원본의 시간은 서버가 잰 `Query_time`이고, 재생의 시간은 재생기가 잰 왕복 시간이다. 재생 쪽에는 네트워크와
드라이버의 시간이 들어 있다. 변경 전후를 비교하려면 재생 중에도 대상의 슬로우 로그를 켜서 로그끼리
비교해야 한다. 지금의 요약에 나오는 "원본 대 재생" 실행 시간은 참고값이다.

## 뒤에 알게 된 것

이 실험은 원본의 연결을 그대로 옮기는 방식(`--unit session`)으로 쟀다. 그 뒤 기본 방식이 메이투안 글을 따라
트랜잭션 단위로 바뀌었다. 스크립트에는 `--unit session`을 적어 두어 이 문서의 조건이 다시 돌아간다.

이 실험의 재생에는 드라이버가 쓰기 문장마다 끼워 넣는 조회(`SELECT @@session.transaction_read_only`)가 섞여
있었다. 실험 03에서 찾아 고쳤고, 그 실험에서 문장 왕복 중앙값이 0.164ms에서 0.144ms로 줄었다. 이 문서의
수치는 고치기 전의 값이다.

## 한계

- 원본과 대상이 같은 서버이고 노트북이다. 포화 처리량은 이 장비에서의 값이다.
- 포화 처리량에는 재생기 쪽 비용이 들어 있다. 같은 장비의 같은 설정에서 sysbench는 초당 약 28,000문장을 냈다(실험 01).
- 30초, sysbench 한 종류의 트래픽이다. 문장이 짧고 균일하다.
