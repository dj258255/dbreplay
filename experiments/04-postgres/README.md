# 실험 04: PostgreSQL에서 녹화, 재생, 비교, 용량 탐색

2026-10-11, PostgreSQL 16 (도커, Apple Silicon 노트북). 재생기는 Java 25, PostgreSQL JDBC 42.7.7.

MySQL에서 한 것을 PostgreSQL에서 그대로 했다. pgbench 부하를 csvlog로 녹화하고, 트랜잭션 단위로 다시 틀고,
설정 변경 전후를 비교하고, 알람이 울리는 배속을 탐색했다.

## 결론

- **녹화부터 용량 탐색까지 전부 돈다.** 문장 41,227개가 오류 없이 재생됐다. 원본도 0개였다.
- **확장 프로토콜로 녹화한 트래픽도 재생된다.** 로그가 본문과 인자를 따로 적는데, 변환기가 인자를 본문에
  끼워 넣는다.
- **변경의 효과가 SQL 모양 단위로 보인다.** `synchronous_commit`을 끄자 `END`가 0.372ms에서 0.023ms로 줄었다.
- **알람이 울리지 않은 가장 높은 배속은 두 번 돌려 9.5와 10.0이었다.** 초당 13,003문장과 13,719문장이고, 수위는 11%와 10%로 과잉이다.
- **부하 지표가 라운드마다 떠진다.** 10배속에서 평균 27%이던 CPU busy가 16배속에서 56%가 됐다.

## 다시 돌리는 법

```sh
./run.sh                 # 약 8분
docker compose down -v
```

녹화 조건은 `pgbench -c 8 -j 4 -T 30 -R 200 -M prepared`, 규모 5다. 서버 설정은 `docker-compose.yml`에 있다.
녹화에 필요한 것은 `log_destination=csvlog`, `log_min_duration_statement=0`, `log_disconnections=on`,
`log_timezone=UTC`다.

이 실험은 두 번 돌렸다. 변환, 1배속 재생, 변경 전후 비교의 수치는 첫 번째 실행의 것이고 원자료는
`out/before-metrics/`에 있다. 용량 탐색과 부하 지표의 수치는 두 번째 실행의 것이고 원자료는 `out/`에 있다.

## 변환

| 항목 | 값 |
|---|---|
| 로그 행 | 82,541 |
| 문장 | 41,227 |
| 연결 종료 | 27 |
| 재생에 쓰지 않아 뺀 행 | 41,287 |
| 시각을 맞춘 문장 | 21,429 |

뺀 행의 대부분은 준비된 문장의 `bind` 줄이다. 실행(`execute`) 줄에 같은 본문과 인자가 다시 나온다.

시각을 맞춘 문장이 절반인 이유는 로그의 시각이 밀리초 단위이기 때문이다. 시작 시각을 "찍힌 시각 - 걸린
시간"으로 구하는데, 같은 밀리초에 찍힌 문장들은 걸린 시간이 긴 쪽이 앞선 것으로 계산된다. 그런 문장은 같은
연결의 앞 문장 시각에 맞춘다. 한 연결 안의 순서는 로그에 적힌 순서 그대로다.

## 1배속 재생 (트랜잭션 단위)

| 항목 | 값 |
|---|---|
| 계획 시간 / 실제 시간 | 31.27초 / 31.27초 |
| 오류 (원본 / 재생) | 0 / 0 |
| 쓴 연결 수 | 31 |
| 늦은 정도 (중앙값 / p99) | 0.26ms / 6.9ms |
| 재생기가 늦어서 1ms 넘게 밀린 문장 | 0.18% |

재생기가 늦은 문장의 비율은 운영체제 타이머에 맡겼을 때 5.44%였다. 전용 스레드가 돌면서 깨우게 바꾼 뒤의
값이 위 표다.

## 변경 전후 비교: synchronous_commit=off

재생할 때마다 대상의 로그를 켜고, 그 로그를 변환한 파일 둘을 비교했다. 원자료는
`out/before-metrics/compare-before-vs-after.txt`에 있다.

| SQL 모양 | 횟수 | 평균 (전 → 후) | 변화 |
|---|---|---|---|
| `END` | 5,889 | 0.372ms → 0.023ms | -93.9% |
| `UPDATE pgbench_branches ...` | 5,889 | 0.124ms → 0.078ms | -37.0% |
| `UPDATE pgbench_accounts ...` | 5,889 | 0.091ms → 0.103ms | +12.7% |

전체 평균은 0.105ms에서 0.051ms로 줄었다. 커밋이 디스크 쓰기를 기다리지 않게 된 것이 `END`에 그대로 나타났다.
`pgbench_branches`는 행이 5개뿐이라 트랜잭션끼리 같은 행의 락을 다툰다. 커밋이 빨라지면 락도 빨리 풀려서
이 `UPDATE`도 함께 줄었다. `pgbench_accounts`의 +12.7%는 한 번씩만 돌린 결과라 편차와 구분하지 못한다.

## 원본 대 재생: 같은 자로 잰 값이 아니다

원본 로그와 변경 전 재생의 로그를 비교하면 문장별 평균이 20~60%씩 다르게 나온다
(`out/before-metrics/compare-prod-vs-before.txt`). 원본은 준비된 문장이라 실행 단계만 찍혔고, 재생은 문장을 통째로 보내
파싱과 계획까지 한 줄에 들어간다. 재생은 트랜잭션들이 원본과 다른 연결에 실려 겹치는 모양도 달라진다.

그래서 비교는 재생끼리 해야 한다. 변경 전 재생과 변경 후 재생은 같은 방식으로 나간 것이라 차이가 변경에서 온다.

## 용량 탐색

알람은 내장 지표 하나에 걸었다. 대상에서 실행 중인 연결(`active_sessions`)이 32개 이상인 채로 0.2초 간격
표본에 3번 연속 잡히면 울린다. 이 기준은 실험을 위해 고른 값이고, 실제로는 사용자가 자기 알람 정책을 넣는다.

| 라운드 | 배속 | 계획 | 실제 | 늦은 정도 p99 | 재생기가 늦은 문장 | 실행 중 최대 | 판정 |
|---|---|---|---|---|---|---|---|
| 1 | 1 | 32.88초 | 32.00초 | 1.5ms | 0.1% | 3 | 버팀 |
| 2 | 2 | 16.44초 | 16.00초 | 1.5ms | 0.1% | 2 | 버팀 |
| 3 | 4 | 8.22초 | 8.00초 | 7.2ms | 0.2% | 8 | 버팀 |
| 4 | 8 | 4.11초 | 4.00초 | 270.3ms | 1.3% | 265 | 버팀 |
| 5 | 16 | 2.06초 | 2.37초 | 1,146.9ms | 14.5% | 277 | 과부하 (알람) |
| 6 | 12 | 2.74초 | 2.67초 | 819.2ms | 5.7% | 266 | 과부하 (알람) |
| 7 | 10 | 3.29초 | 3.21초 | 31.7ms | 0.4% | 60 | 버팀 |
| 8 | 11 | 2.99초 | 2.91초 | 401.4ms | 2.4% | 277 | 과부하 (알람) |

상한은 10배속이다. 녹화 구간이 초당 1,372문장이었으니 상한은 초당 13,719문장이고, 수위는 10%(과잉)다.
계획 시간은 마지막 연결 종료까지이고 실제 시간은 마지막 문장까지라서 실제가 조금 짧다.

8배속 라운드는 실행 중인 연결이 한때 265개까지 올랐지만 버틴 것으로 판정됐다. 32개 이상이 0.6초 동안
이어지지 않았기 때문이다. 순간적인 몰림을 알람으로 볼지는 연속 횟수가 정한다.

같은 절차를 앞서 한 번 돌렸을 때의 상한은 9.5배속이었다(`out/before-metrics/explore.txt`).

평가는 `out/evaluation.json`에 남겼고, `dbreplay check`가 유효하다고 답했다(`out/check-valid.txt`).

## 부하 지표

재생하는 동안 0.2초마다 DB에서 두 지표를, 1초마다 지표 명령(`metrics.sh`)으로 두 지표를 떴다.
칸의 값은 그 라운드의 평균 / 최대다.

| 배속 | 실행 중인 연결 | 100ms 넘게 실행 중인 문장 | CPU busy (%) | Load Average (1분) |
|---|---|---|---|---|
| 1 | 0.1 / 3 | 0 / 0 | 10.9 / 28.1 | 2.1 / 2.4 |
| 2 | 0.2 / 2 | 0 / 0 | 13.8 / 16.6 | 2.4 / 2.4 |
| 4 | 0.5 / 8 | 0 / 0 | 15.4 / 18.3 | 2.2 / 2.3 |
| 8 | 17.7 / 265 | 8.3 / 173 | 22.4 / 30.0 | 2.2 / 2.3 |
| 10 | 5.3 / 60 | 0 / 0 | 27.1 / 39.1 | 4.1 / 4.1 |
| 11 | 39.1 / 277 | 18.6 / 187 | 38.7 / 81.9 | 4.6 / 4.6 |
| 12 | 57.8 / 266 | 28.6 / 169 | 38.8 / 68.5 | 4.2 / 4.2 |
| 16 | 165.4 / 277 | 133.6 / 244 | 55.8 / 84.8 | 2.8 / 4.2 |

녹화하는 30초 동안 운영 쪽에서 뜬 값은 실행 중인 연결 평균 0.28(최대 3), CPU busy 평균 2.6%, Load Average
평균 1.23이었다(`out/record-metrics.txt`).

읽을 때 조심할 것이 있다.

- CPU busy와 Load Average는 재생기 컨테이너에서 읽은 장비 전체의 값이다. DB와 재생기가 같은 장비에 있어서
  재생기의 CPU가 섞여 있다. 재생기의 타이머 스레드가 코어 하나를 계속 쓴다. 1배속 재생의 10.9%와 녹화 때의
  2.6%의 차이가 대부분 그것이다.
- Load Average(1분)는 3초짜리 라운드에는 너무 느린 지표다. 앞 라운드의 부하가 남아 있다. 16배속의 2.8이
  10배속의 4.1보다 낮게 나온 것이 그 때문이다. 이 길이의 라운드에서는 알람으로 쓸 수 없다.
- 100ms 넘게 실행 중인 문장은 버틴 라운드에서 0이고 과부하 라운드에서 수십 개 이상이다. 8배속 라운드만 예외로
  한때 173개까지 올랐다.

## 앞선 실행과의 차이

이 실험은 처음에 연결 단위로 재생하고 재생기가 잰 값으로 과부하를 판정했다. 그때의 상한은 19배속이었다
(`out/session-unit-run/`). 지금의 10배속 안팎과 다른 것은 판정 기준이 다르기 때문이다. 앞의 것은 "재생기가 대상을
못 따라간 지점"이고 지금의 것은 "알람이 울리는 지점"이다.

## 한계

- 원본과 대상이 같은 서버이고 노트북이다.
- 녹화가 30초라 높은 배속의 라운드는 3초 남짓이다. 0.2초 간격으로 3번 연속이라는 알람 조건은 이 길이에
  맞춘 것이다. 실제 알람은 분 단위로 본다.
- `max_connections`가 300이라 과부하 라운드에서는 재생기의 연결이 거기서 막힌다.
- 실패한 문장은 걸린 시간 없이 남고, PostgreSQL에는 숫자 오류 번호가 없어 실패를 1로만 적는다.
- `COPY`와 한 번에 여러 문장을 보내는 단순 질의는 시험하지 않았다.
