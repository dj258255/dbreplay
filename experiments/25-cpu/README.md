# 실험 25: 읽기만 24배속에서 도커의 CPU가 다 차는가

2026-10-19, MySQL 8.4 (도커, Apple Silicon 노트북, 도커에 CPU 12개). #123.

#121 뒤에도 읽기만 튼 탐색은 16~20배속에서 재생기의 한계로 끝난다(실험 22). 재생기 혼자서는 64배속까지 막히지 않는다(실험 23).
남은 후보 가운데 가장 앞의 것은 재생기와 MySQL이 도커의 CPU 12개를 나눠 쓴다는 것이다. 라운드마다 CPU 사용량을 떴다.

## 결론

- **24배속 라운드에서 장비 전체 CPU 사용률은 58~76%(중앙값 73%)였다.** 재기 전에 #123에 적은 기준(85% 이상 / 60% 이하 / 사이)으로
  **"판정하지 못한다"**다. CPU가 평균으로 다 차지는 않았지만, 넉넉하다고 할 만큼 비지도 않았다.
- 다만 MySQL과 재생기 컨테이너의 사용량을 더하면 81~87%(중앙값 84%)로, 장비 전체로 잰 값보다 크다. 둘 중 어느 쪽이 맞는지 모른다.
  어느 쪽으로 봐도 판정은 같다.
- 그때 MySQL은 4.8~5.4코어, 재생기는 4.8~5.1코어를 썼다. 재생기는 MySQL만큼 CPU를 쓴다. 그 가운데 1코어는 `SpinTimer`다.
- 늦은 비율은 사용률보다 먼저 뛴다. 8배속에서 16배속으로 갈 때 사용률은 38 → 60%였는데 늦은 비율은 5.5 → 22.2%(중앙값)였다.

## 다시 돌리는 법

```sh
../22-workers/run.sh      # 트래픽 파일이 없으면 먼저. out/prod.trace.jsonl을 남긴다
caffeinate -i ./run.sh    # 약 3분. REPEAT=5가 기본이다. 결과는 out/. 끝나면 컨테이너를 지운다
python3 summarize.py      # 판정을 다시 찍는다
```

`Bench.java`는 공개된 `Replayer.run`과 `JdbcTarget`을 그대로 부르고, 옆의 스레드가 50ms마다 cgroup의 `cpu.stat`을 읽는다.
재생기 컨테이너에 호스트의 cgroup을 읽기 전용으로 붙인다(`--cgroupns=host -v /sys/fs/cgroup:/hostcg:ro`).

## 조건

- 구성: 실험 24와 같다. MySQL 8.4, sbtest 4×10만 행, `max_connections=1000`. 풀은 #121을 넣은 빌드다(동시에 여는 연결 4개).
- 트래픽: 실험 22의 녹화(sysbench oltp_read_write, 초당 200, 연결 8개, 30초). 읽기만 남기면 84,463문장이다.
- 옵션: `Replayer.Options.atSpeed(s).onlyReads()`. explore `--only reads`와 같다.
- 4배속을 한 번 데운 뒤(세지 않음) 8, 16, 24배속을 한 바퀴로 다섯 바퀴 돌았다.
- 잰 값
  - 장비 전체: 루트 cgroup의 `usage_usec`. 재기 전에 코어 둘을 2초 태워 4,033ms가 느는 것을 보고 장비 전체를 센다고 확인했다.
    컨테이너 안의 `/proc/stat`은 그 컨테이너의 값만 보여 쓰지 않았다(2초에 컨테이너의 쉰 시간만 2,396틱 늘었다).
  - MySQL과 재생기: 각 컨테이너의 cgroup의 `usage_usec`.
  - 구간: 재생 시작 뒤 앞서 넘기는 1초가 지난 때부터 녹화 길이 ÷ 배속만큼. 그 양끝에 가장 가까운 표본끼리 뺐다. 표본은 50ms마다다.
- **노트북이 배터리로 돌았다.** 앞의 실험 22~24는 전원에 꽂혀 있었다. 잰 구간이 계획(24배속 1.27초)과 맞아 잠들지는 않았다.

## 읽은 것

- **두 컨테이너의 합이 장비 전체보다 크다.** 24배속에서 MySQL과 재생기를 더하면 9.7~10.4코어(12코어의 81~87%, 중앙값 84%)인데,
  루트로 잰 장비 전체는 58~76%(8.8코어 남짓)다. 부분의 합이 전체보다 클 수는 없으니 어느 한쪽이 틀렸다. 세 값은 한 표본 안에서
  잇달아 읽으므로 시각이 어긋난 탓은 아니다. 재기 전의 확인(코어 둘을 2초 태움)은 루트만 봤고 컨테이너의 값과 맞대지 않았다.
  컨테이너의 합으로 봐도 84%라 판정(60% 초과 85% 미만)은 같다. 다만 85%의 문턱 바로 아래다.
- 재생기는 24배속(초당 읽기 약 6만 6천 개)에서 4.9코어를 쓴다. `SpinTimer`의 1코어를 빼면 문장 하나에 CPU 약 59µs다. 대부분은
  JDBC 드라이버와 가상 스레드의 몫으로 보지만 나눠 재지 않았다. 실험 23의 아무것도 하지 않는 대상에서는 64배속도 버텼다.
- 평균 73%는 "다 찼다"가 아니다. 다만 두 가지 때문에 이것만으로 "차지 않는다"고도 하지 못한다. 50ms보다 짧은 순간에 다 찼다가
  비는지는 이 표본으로 보이지 않는다. 그리고 도커의 12개 CPU가 맥의 성능 코어인지 효율 코어인지 모른다.
- 24배속의 늦은 비율이 실험 24의 두 번째 실행(47~56%)보다 높았다(79~95%). 배터리로 돈 것, 옆에서 50ms마다 파일을 읽은 것이
  다르다. 어느 쪽 탓인지는 가르지 않았다. 판정은 사용률로만 하므로 바꾸지 않는다.

## 한계

- 평균 사용률이다. 순간의 포화는 보지 않았다.
- 장비 전체(루트 cgroup)와 컨테이너의 합이 맞지 않는다. 어느 쪽이 틀렸는지 가리지 않았다.
- 배터리로 돌았다. 전원에 꽂았을 때와 CPU 성능이 다를 수 있다.
- 같은 장비에서 한 번 돌렸다(배속마다 다섯 번).
