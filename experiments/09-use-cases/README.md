# 실험 09: 글이 든 활용 장면에서 도구가 차이를 잡는가

2026-10-12, MySQL 8.0.46과 8.4.11 (도커, Apple Silicon 노트북). 장면마다 변경 전후를 3번씩, 번갈아 돌렸다. 이슈 #18.

메이투안 글은 이 시스템을 인덱스 변경 검증, 버전 업그레이드 호환성 테스트, 파라미터 튜닝 검증에 쓴다고 했다.
지금까지 해 본 것은 테이블 압축(실험 03)과 `synchronous_commit`(실험 04)뿐이었다. 나머지 장면을 돌려 봤다.
서버 성능 비교는 장비가 하나라 하지 않았다.

## 결론

| 장면 | 가설 | 결과 |
|---|---|---|
| A 인덱스 변경 | 쓰이던 인덱스를 지우면 그 인덱스를 타던 모양이 나빠진 SQL의 맨 위에 온다 | 맞았다. 3번 모두 |
| B 버전 업그레이드 | 8.0의 트래픽이 8.4에서 오류 없이 재생되고, 모양별 평균은 대부분 20% 안이다 | 맞았다. 다만 도구가 깨진 문장을 숫자로만 알려 준다는 것을 찾았다(#36) |
| C 파라미터 변경 | `innodb_flush_log_at_trx_commit`을 2로 바꾸면 `COMMIT`이 줄고 상한이 오른다 | `COMMIT`은 3번 모두 줄었다. 상한은 조건에 따라 방향이 달랐다. 결론 내지 않는다 |

- **세 번 모두 같은 방향으로 20% 넘게 변한 모양만 변경의 효과로 꼽았다.** 그렇게 거르면 장면마다 한두 개가 남는다.
  한 번의 비교에서는 변경과 무관한 모양도 20~40%씩 오르내린다. 39개 모양 중 24~27개는 세 번에서 방향이 갈렸다.
  `compare`의 "나빠진 SQL" 한 번을 그대로 믿으면 안 된다.
- **깨지는 문장은 잡았지만 무엇이 깨졌는지는 도구가 말해 주지 않았다.** 8.4에서 예약어가 된 `QUALIFY`를 별칭으로 쓴
  문장 120개를 일부러 섞었다. `replay`는 "재생 오류 120개"라고만 냈고, `compare`는 "오류가 달라진 SQL: 없음"이라고 냈다.
  MySQL은 구문 오류로 끝난 문장을 슬로우 로그에 적지 않아서, 변경 후의 로그에 그 모양이 아예 없다.
  #36에서 고쳤다. 같은 트래픽을 다시 틀면 `replay`가 "오류 1064, 120번, `SELECT id AS qualify FROM sbtest1 WHERE id = ?`"를 내고
  `compare`가 그 모양을 "앞에만 120번"으로 낸다. 아래의 결과는 고치기 전의 출력이다.

## 다시 돌리는 법

```sh
./run.sh                 # 약 20분. 세 장면의 1배속 재생 18번과 탐색 6번
./run-ceiling.sh         # 약 12분. 파라미터 장면의 상한만 더 무거운 녹화로 다시 잰다
python3 analyze.py a     # 장면별로 세 번의 비교를 모아 본다 (a, b, c)
docker compose down -v
```

## 한 일

녹화는 두 번 했다.

- 8.4에서: sysbench `oltp_read_write`(초당 100 트랜잭션)와 `select_random_points`(초당 20번)를 함께 20초.
  뒤의 것이 `sbtest1`의 `k` 인덱스를 탄다. `oltp_read_write`만으로는 `k_1`을 읽는 문장이 없어 지워도 나빠질 것이 없다.
  문장 40,480개. 장면 A와 C에 쓴다.
- 8.0에서: `oltp_read_write` 20초에 양성 대조 120문장(`SELECT id AS qualify FROM sbtest1 WHERE id = N`)을 섞었다.
  문장 40,503개. 장면 B에 쓴다.

장면마다 "되돌리기 → (변경) → 1배속 재생 → 그때의 서버 로그를 변환"을 전, 후, 전, 후, 전, 후 순으로 했다.
같은 회차의 전과 후를 `compare`에 넣었다(`out/<장면>-compare-<회차>.txt`).

| 장면 | 변경 전 | 변경 후 |
|---|---|---|
| A | 8.4, 덤프 그대로 | 8.4, 되부은 뒤 `ALTER TABLE sbtest1 DROP INDEX k_1` |
| B | 8.0에 8.0의 덤프 | 8.4에 8.0의 덤프 |
| C | 8.4, `innodb_flush_log_at_trx_commit = 1` | 8.4, `= 2` |

## 결과

### A 인덱스 변경

세 번 모두 같은 방향으로 20% 넘게 변한 모양은 하나다.

| SQL 모양 | 횟수 | 평균 (전 → 후), 세 번 | 문장당 읽은 행 (전 → 후) |
|---|---|---|---|
| `SELECT id, k, c, pad FROM sbtest1 WHERE k IN (?+)` | 418 | 0.083 → 15.756ms, 0.084 → 15.711ms, 0.081 → 15.840ms | 0.1 → 100,000 |

세 번 모두 "나빠진 SQL"의 맨 위였고 "읽은 행 수가 2배 이상 늘어난 SQL"에는 이 모양만 나왔다. 재생 오류는 여섯 번 모두 0이다.

인덱스가 없어지면 `k`를 고치는 `UPDATE sbtest1 SET k=k+? WHERE id=?`가 빨라질 것이라고 봤는데 확인되지 않았다.
세 번의 변화가 +5.1%, -38.5%, (세 번째는 상위에 없음)으로 갈렸다.

### B 버전 업그레이드 (8.0 → 8.4)

| | 8.0 (세 번) | 8.4 (세 번) |
|---|---|---|
| 재생 오류 | 0, 0, 0 | 120, 120, 120 |
| 그중 sysbench의 문장 | 0 | 0 |
| 전체 평균 실행 시간 | 0.129, 0.158, 0.136ms | 0.105, 0.110, 0.105ms |
| 변화가 20% 안인 모양 (38개 중) | | 35, 30, 34개 |
| 재생기가 연 연결 | 24개 | 137개 |

- sysbench의 문장은 8.4에서 전부 성공했다. 가설대로다. 다만 sysbench의 문장은 단순하다. 실제 서비스의 SQL에서 무엇이
  깨지는지는 이 실험이 말해 주지 않는다.
- 양성 대조 120문장은 8.4에서 전부 실패했다(`ERROR 1064`, `out/control-on-84.txt`). `replay`의 요약에 오류 120개로 나왔다.
  `compare`에는 "한쪽에만 있는 모양: 앞 1개"로만 나왔다(`out/b-compare-1.txt`).
- 세 번 모두 같은 방향으로 20% 넘게 변한 모양은 `COMMIT` 하나다. 1.607 → 1.194ms, 2.090 → 1.266ms, 1.716 → 1.205ms
  (-25.7%, -39.4%, -29.8%). 두 서버는 다른 컨테이너이고 8.4는 기본값 몇 개가 다르다. 어느 것 때문인지는 확인하지 않았다.
- 연결 수가 다른 것은 재생기 때문이다. 문장이 실패하면 그 연결을 버리고 새로 맺는다. 실패 120개에 연결이 113개 늘었다.
  연결을 맺을 때 드라이버가 보내는 문장도 그만큼 늘어서, 변경 후의 로그가 문장 수는 오히려 많다(40,552 → 40,658).

### C 파라미터 변경 (`innodb_flush_log_at_trx_commit` 1 → 2)

1배속에서 세 번 모두 같은 방향으로 20% 넘게 변한 모양은 둘이다.

| SQL 모양 | 횟수 | 평균 (전 → 후), 세 번 | 변화 |
|---|---|---|---|
| `COMMIT` | 2,003 | 1.266 → 0.917ms, 1.197 → 0.924ms, 1.236 → 0.912ms | -27.5%, -22.8%, -26.2% |
| `UPDATE sbtest4 SET k=k+? WHERE id=?` | 515 | 0.112 → 0.068ms, 0.094 → 0.072ms, 0.092 → 0.066ms | -38.7%, -23.4%, -28.4% |

`COMMIT`은 가설대로다. `UPDATE sbtest4`는 설명하지 못한다. 같은 문장의 다른 테이블(`sbtest1`~`3`)은 이 기준에 들지 않았다.
39개 모양을 세 번씩 보면 우연히 이 기준을 넘는 모양이 하나쯤 나올 수 있다. 효과로 적지 않는다.

`sync_binlog`는 기본값 1 그대로다. 커밋마다 바이너리 로그를 디스크에 내리는 일은 남아 있다.

상한은 두 조건에서 쟀다. 전후를 번갈아 3번씩 탐색했다(알람: 실행 중인 연결 32개 이상이 3번 연속, 또는 100ms 넘는 문장 50개 이상).

| 녹화 | `= 1` (세 번) | `= 2` (세 번) | 방향 |
|---|---|---|---|
| 20초, 초당 100 트랜잭션 (처음 잡은 조건) | 30, 26, 32 이상 | 28, 22, 30 | 세 번 모두 내렸다 |
| 30초, 초당 200 트랜잭션 (다시 잡은 조건) | 11, 12, 11 | 13, 13, 15 | 세 번 모두 올랐다 |

- 처음 잡은 조건은 잘못 잡은 것이다. 첫 탐색이 30배속으로 나온 것을 보고, 나머지를 보기 전에 조건을 바꾼다고 이슈에 적었다.
  녹화가 가벼워서 상한이 탐색의 한도(32배속)에 붙고, 30배속의 라운드는 0.69초다. 알람은 0.2초 간격의 표본이 3번 연속 넘어야 울린다.
  한 라운드에 표본이 서너 개뿐이다.
- 다시 잡은 조건에서는 세 번 모두 올랐다(11~12 → 13~15). 두 범위가 겹치지 않는다. 가설과 같은 방향이다.
- 그런데 처음 조건에서는 세 번 모두 내렸다. 측정으로 보기 어려운 조건이라고 해도, 우연이라면 세 번이 한쪽으로 몰릴 까닭이 없다.
  설명하지 못한다.
- 탐색의 정밀도는 10%다. 11과 13은 두 칸 차이다. 같은 절차의 상한이 7.5~14로 퍼진 적이 있다(실험 03). 3번으로는 약하다.

그래서 "상한이 오른다"는 가설이 맞았다고 적지 않는다. 다시 잡은 조건에서는 그렇게 보였다는 데까지다.
탐색 출력은 `out/c-explore-flush*`(처음 조건)와 `out/c-heavy-explore-flush*`(다시 잡은 조건)에 있다.

## 한계

- 수치는 전부 노트북의 도커에서 나왔다. 원본, 대상, 재생기가 같은 장비를 쓴다. 디스크에 내리는 비용이 실제 서버와 다르다.
- 장면마다 3번이다. 방향이 세 번 같았다는 것이고, 크기의 신뢰 구간을 낼 만한 횟수가 아니다.
- 버전 장면은 8.0의 덤프를 8.4에 되부었다. 실제 업그레이드는 데이터 파일을 그대로 올리는 경우가 많다.
- 인덱스 장면의 읽기(`k IN (...)`)는 맞는 행이 거의 없었다(문장당 0.1행). 인덱스를 타면 아주 싸고 안 타면 전부 읽는,
  차이가 가장 크게 나는 경우다.
