# 실험 26: 미리 여는 연결 수가 늦음을 줄이는가

2026-10-20, MySQL 8.4 (도커, Apple Silicon 노트북, 도커에 CPU 12개, **배터리**). #126, #141.

원문 그림 3의 재생 에이전트는 재생 전에 DB마다 연결을 미리 다 연다. 우리 풀은 16개만 미리 열고 나머지는 재생 도중에 연다.
실험 24에서 도중의 열기가 라운드마다 수백 개였다. `--warm-connections`를 열고 16, 64, 256을 견줬다.

## 결론

- **첫 측정은 처리를 시험하지 못했다.** 세 값 모두 16배속의 늦은 비율 중앙값이 96%였고 재기 전의 기준으로 "줄이지 않는다"였다.
  그런데 256개를 미리 열어도 도중에 311~345개를 또 열었다. 미리 연 연결이 트래픽 파일의 첫 줄(녹화를 켠 `SET GLOBAL`, 데이터베이스
  없음)의 칸에 들어가 `sbtest` 문장이 쓰지 못한 결함이었다(#141). 결과는 `out/first-run/`에 그대로 둔다.
- **#141을 고친 뒤 같은 기준으로 한 번 다시 쟀다.** 중앙값이 16개 14.8%, 64개 10.6%(0.72배), 256개 11.4%(0.77배)였다.
  절반 이하도 0.8배 이상도 아니라 기준대로 **"판정하지 못한다"**이고, 기본값은 16으로 둔다. 다시 잰 것은 판정을 바꾸려는 것이 아니라
  처리가 들어가지 않았기 때문이며, 그 까닭은 재기 전에 #126에 적었다.
- 미리 연 연결이 쓰이자 도중에 연 연결이 줄었다. 16개일 때 157~231개, 256개일 때 14~39개였다(첫 측정은 311~345개).
- 같은 배터리 조건에서 미리 열기 16개의 늦은 비율이 96.3%(결함 있음)에서 14.8%(고친 뒤)로 내려갔다. 다만 한 번씩 돌린 것이고
  두 실행 사이에 장비 상태가 섞여 이 차이를 다 결함 탓으로 돌리지는 않는다.

## 다시 돌리는 법

```sh
../22-workers/run.sh      # 트래픽 파일이 없으면 먼저. out/prod.trace.jsonl을 남긴다
caffeinate -i ./run.sh    # 약 3분. REPEAT=3이 기본이다. 결과는 out/. 끝나면 컨테이너를 지운다
python3 summarize.py      # 판정을 다시 찍는다. OUT=out/first-run을 앞에 붙이면 첫 측정
```

`Bench.java`는 실험 24의 측정 도구에 미리 여는 수(`Replayer.Options.withWarmConnections`)만 더했다. 첫 측정은 #141 전의 빌드,
다시 잰 것은 #141을 넣은 빌드다.

## 조건

- 구성: 실험 24와 같다. MySQL 8.4, sbtest 4×10만 행, `max_connections=1000`. 풀은 동시에 여는 연결 4개(#121).
- 트래픽: 실험 22의 녹화(sysbench oltp_read_write, 초당 200, 연결 8개, 30초). 읽기만 남기면 84,463문장이다.
- 옵션: `Replayer.Options.atSpeed(16).onlyReads().withWarmConnections(n)`. 연결 상한 500.
- 4배속을 미리 여는 수 16으로 한 번 데운 뒤(세지 않음), 16배속을 16, 64, 256의 순서로 번갈아 세 바퀴 돌았다. 한 JVM 안이다.
- "도중에 연 연결"은 결과를 받는 가상 스레드에서 그 문장이 연결을 새로 열었는지 센 것이다(실험 24와 같은 방법). 미리 연 연결은 세지 않는다.
- 두 측정 모두 노트북이 배터리로 돌았다. 잰 구간이 계획(1.91초)과 맞아 다시 잰 쪽은 잠들지 않았다.

## 읽은 것

- 256개를 미리 열어도 늦은 비율이 6~12%로 남았다. 도중에 연 연결이 14~39개로 줄었는데도 그렇다. 남은 늦음은 연결 열기만의
  탓이 아니다. 실험 25에서 재생기가 MySQL만큼 CPU를 쓴 것과 이어 볼 일이지만 재지 않았다.
- 미리 여는 데 드는 시간은 크지 않았다. "합친 초"에서 "재생 초"를 빼면 16개 1.0초, 256개 1.1초 남짓이다. 여기에는 미리 열기 말고
  앞서 넘기는 1초가 들어 있다.
- 세 번이 크게 갈린 칸이 있다(16개의 40.7%, 64개의 31.9%). 바퀴마다 한 번씩만 튀어 우연과 가르지 못한다.

## 한계

- 노트북이 배터리로 돌았다. 전원에 꽂았을 때(실험 24의 두 번째 실행, 같은 16개 미리 열기에 결함 있음, 중앙값 17.8%)와 견주지 않는다.
- 16배속 하나만 쟀다. 탐색의 한계(실험 22)가 바뀌었는지는 재지 않았다.
- 같은 장비에서 측정마다 한 번 돌렸다(값마다 세 번).
