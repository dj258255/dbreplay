# 실험 06: 실행 계획이 바뀐 것이 읽은 행 수로 드러나는가

2026-10-12, MySQL 8.4.11 (도커, Apple Silicon 노트북). 한 번 돌렸다.

`compare`에 읽은 행 수와 오류의 비교를 더하면서(#19), 실험 02에서 우연히 만났던 실행 계획 변화를 일부러 다시 만들어
그 비교가 잡아내는지 봤다.

## 결론

- **잡아낸다.** 통계를 틀어 놓은 샌드박스에서 `sbtest1`의 범위 조회가 읽는 행 수가 문장당 100에서 100,000으로,
  1,000배가 됐고 `compare`가 그 모양 셋을 냈다.
- **읽은 행 수는 원인을 가리킨다.** 실행 시간으로 보면 `COMMIT`(+560%)과 `UPDATE`(+348%)도 함께 나빠졌다. 풀 스캔이
  장비를 차지해서 따라 느려진 것이다. 읽은 행 수가 늘어난 것은 범위 조회뿐이다.

## 다시 돌리는 법

```sh
./run.sh                 # 약 3분
docker compose down -v
```

## 한 일

1. sysbench 부하를 20초 녹화한다(초당 100트랜잭션).
2. 되돌린 샌드박스에 1배속으로 틀어 그때의 서버 로그를 얻는다. 통계가 맞는 쪽이다.
3. 다시 되돌린 뒤 `stale-stats.sh`로 `sbtest1`의 통계를 행 수 46으로 고쳐 놓고 같은 트래픽을 튼다.
   실험 02에서 덤프를 되부은 직후에 남아 있던 값이다. `EXPLAIN`이 `type: ALL`을 낸다(`out/explain-stale.txt`).
4. 두 로그를 `compare`에 넣는다(`out/compare.txt`).

## 결과

읽은 행 수가 2배 이상 늘어난 SQL

| SQL 모양 | 횟수 | 문장당 읽은 행 (전 → 후) | 배율 |
|---|---|---|---|
| `SELECT c FROM sbtest1 WHERE id BETWEEN ? AND ?` | 486 | 100 → 100,000 | 1,000배 |
| `SELECT SUM(k) FROM sbtest1 WHERE id BETWEEN ? AND ?` | 494 | 100 → 100,000 | 1,000배 |
| `SELECT DISTINCT c FROM sbtest1 WHERE id BETWEEN ? AND ? ORDER BY c` | 492 | 200 → 100,100 | 500배 |

실행 시간이 나빠진 SQL

| SQL 모양 | 평균 (전 → 후) | 읽은 행 수가 늘었는가 |
|---|---|---|
| `SELECT c FROM sbtest1 WHERE id BETWEEN ? AND ?` | 0.071ms → 15.892ms | 예 |
| `COMMIT` | 1.412ms → 9.310ms | 아니오 |
| `UPDATE sbtest1 SET k=k+? WHERE id=?` | 0.080ms → 0.358ms | 아니오 |
| `SELECT c FROM sbtest1 WHERE id=?` | 0.035ms → 0.114ms | 아니오 |

전체 평균은 0.121ms에서 1.370ms가 됐다. 재생 오류는 양쪽 다 0이고 오류가 달라진 SQL은 없다.

상위 3개만 내서 `ORDER BY`가 붙은 범위 조회 하나(445번)는 표에 없다. 그것도 읽은 행 수가 늘었다.

## 한계

- 한 번 돌렸다. 풀 스캔 여부는 실행마다 달라질 값이 아니지만 실행 시간의 배율은 달라진다.
- 통계를 손으로 고쳐 만든 상황이다. 실제로는 인덱스가 빠졌거나 버전이 올라 옵티마이저가 달라졌을 때 같은 모습이 나온다.
- PostgreSQL의 로그에는 읽은 행 수가 없어 이 비교가 나오지 않는다. `compare`가 없다고 알려 준다.
- 오류의 비교는 단위 테스트로만 확인했다. 실험에서 오류가 달라진 경우를 만들지 않았다.
