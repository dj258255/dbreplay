# 실험 13: 리터럴을 가린 트래픽으로 재생해도 결과를 믿을 수 있는가

2026-10-12, MySQL 8.4와 PostgreSQL 16 (도커, Apple Silicon 노트북). 수준마다 1배속 3번, 탐색 3번. 이슈 #11.

녹화 파일에는 리터럴 값이 그대로 남는다. 개인정보가 섞인 SQL을 운영 밖으로 가져갈 수 없으면 이 도구는 쓸 수 없다.
`convert --mask`를 만들고, 가린 트래픽으로 재생한 결과가 가리지 않은 것과 얼마나 다른지 봤다.

| 수준 | 가리는 것 |
|---|---|
| `none` | 없음 |
| `strings` | 글자로 된 값과 10자리 이상의 숫자. 짧은 숫자는 식별자로 보고 둔다 |
| `all` | 숫자까지 전부 |

길이와 글자의 종류를 지키고, 같은 값은 같은 값으로 바꾼다. 날짜와 시각 모양의 값은 가리지 않는다.

## 결론

- **`strings`는 가리지 않은 재생과 구분되지 않았다.** 두 기종에서 재생 오류 0개. 세 번 모두 같은 방향으로 20% 넘게 변한 모양이 없다.
  상한의 범위도 겹친다(MySQL 13, 13, 14 대 13, 13, 15). 가설의 앞쪽은 "차이를 보지 못했다"까지다. "10% 안에서 같다"고는 적지 못한다.
  가리지 않은 재생끼리도 38개 모양 중 7~9개가 10%를 넘게 달랐다.
- **MySQL에서 `all`은 재생이 성립하지 않았다.** 30초 분량의 1배속 재생이 처음에는 9분, 다시 2분의 한도를 두고 틀었을 때도 끝나지 않았다.
  원본의 범위 조회는 100행이다(`BETWEEN 50100 AND 50199`). 두 끝이 따로 바뀌어 `BETWEEN 22701 AND 63063` 같은 4만 행짜리가 됐다.
  값 하나하나의 자릿수는 지켰지만 값들 사이의 관계는 지키지 못했다.
- **PostgreSQL에서 `all`은 끝까지 돌지만 다른 부하다.** `UPDATE` 셋이 세 번 모두 빨라졌다(-8~-26%). 가리지 않은 재생끼리는
  `pgbench_tellers`와 `pgbench_accounts`의 `UPDATE`가 ±2% 안에서 움직였다. `END`(커밋)는 달라지지 않았다(-3~+2%).
  가설의 뒤쪽은 절반만 맞았다. 미리 정한 기준(세 번 모두 20% 넘게)에는 들지 않아서 효과의 크기로 적지는 않는다.
- **기본으로 삼을 수준은 `strings`다. 대가는 이렇다.** 짧은 숫자로 된 개인정보(나이, 금액, 9자리 이하의 번호)와 날짜로 된
  개인정보(생년월일)는 남는다. 어떤 열이 개인정보인지는 도구가 모른다. 가린 파일을 밖으로 내보내도 되는지는 사람이 봐야 한다.

## 이 실험이 말해 주지 않는 것

sysbench와 pgbench의 값에는 뜻이 없다. 글자로 된 값을 조건으로 찾는 문장도, 글자 열의 유일 키도 없다. `strings`가 깨뜨릴 만한 것이
이 트래픽에는 처음부터 없다. pgbench에는 글자로 된 값이 아예 없어서 PostgreSQL의 `strings` 파일은 `none`과 같다(`out/pg-samples.txt`).
실제 서비스의 SQL에서 `strings`가 재생을 깨뜨리는지(이메일로 찾기, 유일 키 충돌, `LIKE 'abc%'`)는 해 보지 않았다.
단위 테스트는 같은 값이 같은 값으로 바뀌는 것까지만 본다.

가림이 개인정보를 빠짐없이 지우는지도 이 실험이 잰 것이 아니다.

## 다시 돌리는 법

```sh
./run.sh                 # 두 기종. 약 50분
./run.sh mysql           # 한 기종만 (mysql, postgres)
python3 analyze.py out/mysql-compare-strings-1.txt out/mysql-compare-strings-2.txt out/mysql-compare-strings-3.txt
docker compose down -v
```

## 한 일

1. 30초 녹화한다. MySQL은 sysbench `oltp_read_write` 초당 200 트랜잭션(문장 117,302개), PostgreSQL은 pgbench 초당 200 트랜잭션.
2. 같은 서버 로그를 세 수준으로 변환한다. 같은 문장이 수준마다 어떻게 보이는지는 `out/mysql-samples.txt`, `out/pg-samples.txt`에 있다.
3. 수준을 번갈아 1배속으로 3번씩 틀고, 그때의 서버 로그를 같은 회차의 `none`과 `compare`에 넣는다.
4. 기준선으로 `none`끼리도 비교한다(1-2, 2-3, 1-3).
5. 수준을 번갈아 3번씩 탐색한다. 알람은 실행 중인 연결 32개 이상(3번 연속)이다.

MySQL의 `all`은 처음 계획에서 뺐다. 첫 실행에서 재생이 끝나지 않는 것을 보고 멈췄고(`out/first-attempt`), 이유를 이슈에 적은 뒤
2분의 한도를 두고 한 번만 트는 것으로 바꿨다.

## 결과

### MySQL

| | `none` | `strings` | `all` |
|---|---|---|---|
| 1배속 재생 오류 (세 번) | 0, 0, 0 | 0, 0, 0 | 재생이 끝나지 않음 |
| 상한 (세 번) | 13, 13, 14 | 13, 13, 15 | 재지 않음 |

모양별 평균의 변화(38개 모양)

| 비교 | 10% 안인 모양 (세 번) | 20% 안인 모양 (세 번) | 세 번 모두 같은 방향으로 20% 넘게 |
|---|---|---|---|
| `none` 대 `none` (기준선) | 31, 29, 30 | 36, 32, 36 | 없음 |
| `none` 대 `strings` | 29, 28, 30 | 35, 36, 35 | 없음 |

`all`을 2분의 한도로 틀었을 때: 한도 안에 끝나지 않았다. 그때 서버에 실행 중인 연결이 497개였다(서버의 상주 스레드 하나가 들어 있다.
재생기의 연결 한도는 500이다). 전부 `SELECT DISTINCT c FROM sbtestN WHERE id BETWEEN ? AND ? ORDER BY c` 꼴이었다(`out/mysql-all-state.txt`).
첫 실행에서는 9분째에 같은 문장 494개가 돌고 있었고 락 대기는 0, MySQL 컨테이너의 CPU는 659%였다.

### PostgreSQL

| | `none` | `strings` (파일이 `none`과 같다) | `all` |
|---|---|---|---|
| 1배속 재생 오류 (세 번) | 0, 0, 0 | 0, 0, 0 | 2, 2, 2 |
| 상한 (세 번) | 7.5, 13, 14 | 12, 14, 12 | 13, 13, 13 |

`all`의 오류 2개는 녹화에 섞인 실험 스크립트의 문장이다(`ALTER SYSTEM SET log_min_duration_statement = -1`의 값이 바뀌어 실패한 것과
카탈로그 조회 하나). 41,000문장 중 2개다.

모양별 평균 실행 시간(ms)의 변화. 한 칸에 세 번의 값이 있다.

| SQL 모양 | `none` 대 `none` | `none` 대 `strings` | `none` 대 `all` |
|---|---|---|---|
| `UPDATE pgbench_branches ...` | +18.8%, -3.7%, +14.5% | +26.6%, -4.3%, -6.8% | -14.3%, -16.1%, -25.8% |
| `UPDATE pgbench_accounts ...` | -0.1%, +1.7%, +1.6% | +8.6%, -0.0%, -7.7% | -8.4%, -20.4%, -25.0% |
| `UPDATE pgbench_tellers ...` | +1.4%, +0.7%, +2.1% | +0.3%, -5.9%, +0.7% | -15.7%, -15.1%, -16.7% |
| `END` | +3.8%, +3.2%, +7.1% | +30.5%, +0.6%, -1.9% | +1.5%, -1.5%, -3.4% |
| `SELECT abalance ...` | +2.0%, +0.2%, +2.2% | +2.5%, +2.5%, -2.2% | +0.1%, -3.2%, -9.0% |

- `strings`의 파일은 `none`과 같다. 그런데도 한 번은 `END`가 +30.5%, `UPDATE pgbench_branches`가 +26.6%였다. 같은 것을 틀어도 이만큼 다르다.
- `all`에서 `UPDATE` 셋이 빨라진 까닭은 재지 않았다. 식별자가 다른 값으로 바뀌면 없는 행을 가리키는 문장이 생긴다
  (`pgbench_branches`는 5행인데 `bid`가 1~9로 바뀐다). 그런 문장은 고칠 행이 없어 빨리 끝난다. 몇 개가 그랬는지는 세지 않았다.

## 한계

- 수준마다 3번이다. 상한은 세 수준의 범위가 겹쳐서 차이를 보지 못했다는 것이고, 차이가 없다는 것이 아니다.
  PostgreSQL의 `none`에서 7.5가 한 번 나왔다. 8배속 라운드 하나에서 알람이 울린 것이다.
- 한 장비의 도커다.
- "긴 숫자"의 기준 10자리, 날짜 모양을 가리지 않는 것, 글자 종류를 지키는 방식은 작업 세션이 고른 것이다.
- `all`이 값들 사이의 관계(범위의 폭, 순서)를 지키게 하는 방법은 만들지 않았다. 식별자까지 가려야 한다면 그것이 먼저다.
- PostgreSQL의 달러 인용 문자열(`$$...$$`), 16진수, 지수 표기의 숫자, 주석 안의 값은 가리지 않는다.
