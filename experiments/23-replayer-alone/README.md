# 실험 23: 재생기 혼자서도 15~20배속에서 막히는가

2026-10-19, DB 없음 (도커, Apple Silicon 노트북, 도커에 CPU 12개). #117.

실험 07과 22에서 읽기만 문장 단위로 튼 탐색은 15~20배속 언저리에서 재생기가 먼저 막혔다. 막히는 곳이 재생기 안인지는
가리지 않았다. 재생기의 `SpinTimer`는 잠금 하나짜리 우선순위 큐를 쓰고, 도는 스레드가 쉬지 않고 그 잠금을 잡는다.
#113과 #115의 결과와 어긋나지 않는 후보라서 DB를 빼고 재생기만 돌려 봤다.

## 결론

- **재생기 혼자서는 64배속까지 막히지 않았다.** 아무것도 하지 않는 대상에 실험 22의 트래픽을 `--only reads`와 같은 옵션으로
  틀자, 배속 8~64에서 늦은 문장의 비율이 세 번 모두 2.7% 이하였다. explore가 왜곡으로 보는 20%에 한 번도 닿지 않았다.
  재기 전에 #117에 적은 기준으로 **"재생기 혼자서는 막히지 않는다"**다.
- 그래서 타이머의 잠금은 실험 22의 한계를 만들지 않는다. 64배속은 초당 읽기 문장 약 18만 개다(문장 84,463개를 0.48초에).
  실험 22가 막힌 20배속은 그 3분의 1이 안 된다.
- 실험 22의 한계는 재생기가 진짜 대상과 일할 때 생긴다. 무엇인지는 재지 않았다. 아래 "읽은 것"에 후보를 적었다.

## 다시 돌리는 법

```sh
../22-workers/run.sh      # 트래픽 파일이 없으면 먼저. out/prod.trace.jsonl을 남긴다
caffeinate -i ./run.sh    # 약 1분. REPEAT=3이 기본이다. 결과는 out/
python3 summarize.py      # 판정을 다시 찍는다
```

`run.sh`는 `installDist`로 재생기를 빌드하고 `Bench.java`를 호스트의 JDK 25로 컴파일한 뒤, 실험 22와 같은 실행 이미지
(`../runner`) 안에서 돌린다. `Bench`는 공개된 `Replayer.run`을 그대로 부른다. 재생기 쪽 코드는 바꾸지 않았다.

## 조건

- 트래픽: 실험 22의 녹화(sysbench oltp_read_write, 초당 200, 연결 8개, 30초, 120,677줄). 읽기만 남기면 84,463문장이다.
- 옵션: `Replayer.Options.atSpeed(s).onlyReads()`. explore `--only reads`가 쓰는 것과 같다(문장 단위, 연결 상한 500,
  미리 여는 연결 16개, 1초 앞서 넘김, 1ms보다 늦으면 늦은 문장).
- 대상: 연결을 바로 돌려주고, 문장을 받자마자 성공으로 돌려준다. 그러니 늦은 문장은 모두 재생기 안에서 생긴다.
- 배속 8, 16, 24, 32, 48, 64를 한 바퀴로 세 바퀴 돌았다. 한 JVM 안에서 낮은 배속부터 돈다. explore의 라운드와 같은 순서다.
- 걸린 시간이 계획(30초 ÷ 배속)과 0.1초 안에서 맞았다. 장비가 잠들지 않았다.

## 읽은 것

- 늦은 문장은 낮은 배속(8~24)에서 오히려 조금 많았다(0.5~2.7%, p99 2~5ms). 배속이 낮으면 한 바퀴가 길어 그 사이에
  무엇인가(가비지 수집이나 JIT 같은) 끼어들 기회가 많은 것으로 보지만 재지 않았다. 어느 쪽이든 20%와는 거리가 멀다.
- 실험 22와 다른 것은 셋이다. 이 가운데 무엇이 한계를 만드는지는 재지 않았다.
  1. 재생기가 DB와 CPU 12개를 나눠 쓴다. 이번에는 재생기 혼자 썼다.
  2. 진짜 대상은 문장마다 왕복을 기다린다. 동시에 실행 중인 문장이 늘고, 연결 드라이버가 CPU를 쓴다.
  3. 풀에 쉬는 연결이 없으면 재생기는 그 자리에서 새 연결을 연다(`SessionPool.acquire`). 늦음은 연결을 받은 뒤에 재므로
     (`Replayer.runAlone`) 연결을 여는 몇 ms가 그대로 늦음에 들어간다. 대상이 느려져 동시에 필요한 연결이 미리 연 16개를
     넘으면 늦은 문장이 한꺼번에 생길 수 있다. 실험 22의 8배속 라운드에서 연결이 튄 것과 맞물리는지는 보지 않았다.

## 한계

- 대상이 아무것도 하지 않으므로 가상 스레드가 입출력에서 기다리지 않는다. 진짜 대상에서는 동시에 살아 있는 스레드와 연결이
  훨씬 많다. 이 실험이 말하는 것은 "타이머와 넘겨주는 스레드는 64배속을 감당한다"까지다.
- 트래픽 하나(sysbench, 30초)로만 쟀다. 문장이 고르게 퍼진 트래픽이다. 한순간에 몰리는 트래픽은 재지 않았다.
- 같은 장비에서 한 번 돌렸다(배속마다 세 번).
