# 실험 16: 원문 대조에서 메운 것들이 실제 DB에서 도는가

2026-10-14, MySQL 8.4.11(GTID 복제)과 PostgreSQL 16(스트리밍 복제), 도커, Apple Silicon 노트북. 상위 이슈 #59.

원문을 항목별로 다시 대조해(`docs/verify/ARTICLE.md`) 찾은 구멍을 하나씩 메우면서, 단위 테스트가 통과한 뒤 실제 DB에서 한 번씩 돌려 본 기록이다.
수치를 재는 실험이 아니라 기능이 도는지를 보는 확인이다. 기능마다 스크립트 하나(`check-<이슈 번호>.sh`)와 그 출력(`out/`)이 있다.

## 다시 돌리는 법

```sh
./setup.sh               # 두 기종의 주종을 세우고 데이터를 넣는다. 약 2분
./check-56.sh            # 기능마다 하나씩
docker compose down -v
```

## #56 스냅샷 명령

`dbreplay snapshot`으로 뜬 덤프를 `reset`으로 되부으면 바꿔 둔 행이 원래대로 돌아오는가.

| | 뜨기 전 | 바꾼 뒤 | 되돌린 뒤 (주 DB, 종 DB) |
|---|---|---|---|
| MySQL: `sbtest1`의 행 수, `k`의 합 | 100,000 / 5,009,335,300 | 99,000 / 4,909,269,067 | 100,000 / 5,009,335,300 (둘 다) |
| PostgreSQL: `pgbench_accounts`의 행 수, 잔액의 합 | 500,000 / 0 | 499,000 / -7,000 | 500,000 / 0 (둘 다) |

- MySQL은 GTID가 켜져 있다. 덤프에 `GTID_PURGED`가 0번 나오고 되붓기가 걸리지 않았다. 79.2MB를 3.2초에 떴다.
- **단위 테스트로는 보지 못한 것이 여기서 나왔다.** 실행 이미지의 `pg_dump`는 18.6이고 서버는 16이다. 새 `pg_dump`는 덤프의 머리에
  `SET transaction_timeout = 0;`을 넣는데 16은 그 설정을 몰라서 되붓기가 실패했다. 서버가 모르는 설정의 줄을 덤프의 머리에서 빼게 고쳤다.
  지금까지의 실험은 서버 안의 `pg_dump`를 써서 이 일이 드러나지 않았다.
- 실행 이미지의 `mysqldump`는 오라클의 8.4.11이다. MariaDB의 `mysqldump`로 뜨는 쪽(GTID 옵션을 붙이지 않는 쪽)은 단위 테스트로만 봤다.
- PostgreSQL의 첫 확인은 앞의 실패한 실행이 남긴 상태에서 시작해 전과 후가 처음부터 같았다. 데이터를 다시 만들고 돌린 것이 위의 표다.

## #57 하드웨어를 무효 조건에

`--profile-command`가 낸 값이 평가 파일에 남고, 그 값이 바뀌면 `check`가 무효로 답하는가. `host.sh`가 CPU 수, 메모리, 기종 이름을 낸다.

| 경우 | `check`의 답 |
|---|---|
| 같은 장비 | 유효하다. "하드웨어는 설정 명령이 낸 값으로 비교했다" |
| CPU 수를 12에서 2로 바꿈 | 무효다. "버전이나 파라미터가 바뀌었다: host.cpus 12 → 2" |
| 명령을 주지 않음 | 유효하다. "평가 파일에 하드웨어가 있지만 --profile-command를 주지 않아 비교하지 않았다" |
| 아무것도 내지 않는 명령 | 유효하다. "...--profile-command가 아무 값도 내지 않아 비교하지 않았다" |

- 평가 파일에는 `host.cpus`, `host.memory_gb`, `host.model`이 남았고 명령의 원문(`host.sh`)은 0번 나온다.
- 무효의 이유가 "버전이나 파라미터가 바뀌었다"라는 말로 나온다. 하드웨어가 바뀐 것인데 문구가 그것을 가르지 않는다. 고치지 않았다.
- `host.sh`는 재생기 컨테이너가 보는 값을 낸다. DB 서버의 사양이 아니다. 실제로는 사용자가 서버의 사양을 내는 명령을 줘야 한다.

## #63 스냅샷과 트래픽 파일의 권한

`snapshot`과 `convert`가 만든 파일을 소유자만 읽고 쓸 수 있는가. 컨테이너 안의 임시 폴더에 `644`인 빈 파일을 먼저 만들어 두고 그 위에 썼다.

| 파일 | 권한 | 크기 |
|---|---|---|
| MySQL 스냅샷 | 600 | 79.2MB |
| PostgreSQL 스냅샷 | 600 | 47.9MB |
| 트래픽 파일 | 600 | 207바이트 |

고친 뒤에 #56의 확인(스냅샷을 뜨고 되돌리기)을 다시 돌려 두 기종 모두 원래대로 돌아오는 것을 봤다.
맥의 도커가 마운트한 폴더는 권한을 그대로 옮기지 않아서 권한은 컨테이너 안에서 봤다.

## #54 운영 QPS를 도구가 잰다

`sample`이 낸 값이 부하 도구가 보고한 값과 맞는가(완료 조건은 10% 안).

| | 부하 도구의 보고 | `sample`의 평균 | 차이 |
|---|---|---|---|
| MySQL `qps` (sysbench 초당 200 트랜잭션, 20초) | 초당 4,023문장 | 3,928 | -2.4% |
| PostgreSQL `tps` (pgbench 초당 200 트랜잭션, 20초) | 초당 198.4 | 204.8 | +3.2% |

- 한가할 때 MySQL의 `qps`는 평균 0.41이다. 표본기 자신의 조회(표본 하나에 셋)를 뺀 값이다.
- 한가할 때 PostgreSQL의 `tps`는 평균 6.96이다. 표본기의 것을 뺀 뒤에도 남는다. 서버 안의 일(자동 청소, 통계 수집)로 짐작하지만 확인하지 않았다.
  부하를 걸었을 때 3% 높게 나오는 것과 크기가 맞는다.
- PostgreSQL은 `qps`를 내지 않는다. 문장 수를 세는 카운터가 기본으로 없다. MySQL은 `tps`를 내지 않는다. 자동 커밋된 문장을 세는 카운터가 없다.
- `check --current-qps 1200`: "지금의 초당 1200문장으로 다시 계산한 수위: 68% (건강 구간 30~50%) → 부족".
- 1차 구현으로 돌린 값은 3,879(-2.1%)와 205.9(+4.0%)였다. 위는 검토 뒤 고친 것으로 다시 돌린 값이다.

## #55 느리게 끝난 문장의 수, #66 없는 지표에 건 알람

`slow_finished_total`이 서버가 센 값과 맞는가, 알람으로 걸리는가.

- 16배속 재생 한 번: 서버의 분포로 센 100ms 넘는 문장이 1,318개, 지표의 마지막 값이 1,317개.
- `--alarm-total "slow_finished_total>=50"`으로 탐색: 16, 14, 13배속 라운드가 "slow_finished_total이(가) 50 이상"으로 과부하 판정되고 상한이 12.00배속으로 나왔다.
  1차 구현으로 돌렸을 때는 8배속에서 울려 7.50이 나왔다. 상한이 실행마다 다른 것은 실험 12에서 본 그대로다.
- 실험 03은 같은 알람을 사용자 명령(`alarm-slow.sh`)으로 걸고, 라운드마다 서버의 분포를 비우는 명령(`ready.sh`)을 따로 돌렸다. 이제 둘 다 필요 없다.
- 지표는 기준 시간이 걸쳐 있는 칸까지 센다. 서버의 분포가 칸 단위라 정확히 가를 수 없어서, 덜 세는 것보다 더 세는 쪽을 골랐다.

없는 지표에 건 알람이 멈추는가.

| 건 알람 | 결과 |
|---|---|
| `--alarm-metric "active_session>=32"` (끝의 s가 빠졌다) | 멈췄다. "알람에 건 지표 'active_session'이(가) 이 라운드에 한 번도 떠지지 않았다 ... 뜬 지표: active_sessions, qps, slow_finished_total, slow_running" |
| PostgreSQL에 `--alarm-total "slow_finished_total>=50"` | 멈췄다. "... 뜬 지표: active_sessions, slow_running, tps" |

고치기 전에는 두 경우 모두 오류 없이 한도까지 "버팀"으로 올라갔을 것이다.
