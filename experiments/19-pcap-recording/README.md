# 실험 19: 패킷 캡처로 녹화한다

2026-10-15~17, MySQL 8.4와 PostgreSQL 16 (도커, Apple Silicon 노트북). 이슈 #79.

글의 첫 목표는 재생과 평가가 운영 클러스터에 영향을 주지 않는 것이다. 글은 DB 커널에서 SQL을 수집한다. 이 도구는 모든 문장을 서버 로그로 남기게 했고,
그 값으로 포화 상태의 처리량이 MySQL 12%, PostgreSQL 16% 줄었다(실험 15). DB가 로그를 쓰지 않게 하려고 패킷 캡처를 읽는 변환기를 만들었다
(`convert --from mysql-pcap|postgres-pcap`). 캡처는 DB 컨테이너의 네트워크에 붙은 별도 컨테이너의 tcpdump가 한다.

## 결론

- **캡처한 것은 서버 로그와 문장 하나까지 맞는다.** 같은 부하를 둘로 동시에 떠서 변환하자 MySQL 20,062 대 20,060, PostgreSQL 6,682 대 6,680이었다.
  양쪽에서 빠진 둘은 실험 스크립트가 컨테이너 안의 루프백으로 보낸 관리 문장(로그 켜기, 버전 조회)이다. 캡처가 볼 수 없는 자리다.
  MySQL은 준비한 문장(sysbench), PostgreSQL은 확장 질의(`pgbench -M prepared`)였다. 인자를 끼워 넣은 문장의 모양이 서버 로그와 같다.
- **하지만 캡처가 패킷을 놓치기 쉽다.** 이 결론에 닿기까지 1부를 네 번 돌렸다(아래 "1부를 네 번 돈 이유"). 캡처 파일을 느린 곳에 쓰거나 멈추는 때를 잘못 잡으면
  패킷을 버렸다. 도구는 놓친 연결을 해석하지 않고 그 수를 알린다. 지어내지 않는다.
- **캡처의 부담은 판정하지 못했다.** 2부를 세 번 쟀다. 첫 번째는 tcpdump가 패킷 대부분을 버리던 설정이라(호스트 폴더에 씀) 캡처를 다 하지 않은 부담이다.
  두 번째와 세 번째는 캡처와 상관없이 장비가 두 상태를 오가 끔과 켬이 섞였다. 두 실행이 모두 정상인 쌍만 보면 MySQL은 -8.9, -8.0, -3.7%로
  서버 로그(12%)보다 작고 5%를 넘는다. 세 쌍뿐이라 판정에 쓰지 않는다. PostgreSQL은 그런 쌍이 하나다.

## 다시 돌리는 법

```sh
./part1.sh        # 1부: 같은 부하를 서버 로그와 패킷 캡처로 동시에 떠서 맞춰 본다. 약 5분
./part2.sh        # 2부: 캡처의 부담. 속도 제한 없이 8개 연결로 30초, 끔과 켬을 번갈아 5번. 약 12분
docker compose down -v
```

`run.sh`는 첫 실행의 1부와 2부다. 결과를 다시 낼 수 있게 그대로 두었다(캡처를 호스트 폴더에 쓰고, 부하가 끝나자마자 멈춘다).

## 1부를 네 번 돈 이유

| 차례 | 캡처의 설정 | MySQL (서버 로그 대 캡처) | 무엇이 틀렸나 |
|---|---|---|---|
| 1 (`run.sh`) | 호스트 폴더에 씀, 부하가 끝나자마자 멈춤 | 19,702 대 19,671 | 연결 넷 가운데 둘의 마지막 트랜잭션과 네 연결의 끝(`COM_QUIT`)이 없다. 멈출 때 남은 패킷이 파일에 쓰이지 않았다 |
| 2 | 3초 기다렸다 멈춤 | 17,902 대 10,619 | tcpdump가 커널에서 패킷 3,098개(7.9%)를 버렸다. 네 연결 모두 조각을 놓쳤다 |
| 3 | 커널 버퍼 64MB(`-B 65536`) | 21,782 대 15,668 | 커널에서 버린 것은 0이지만 필터에 걸린 47,448개 가운데 34,181개만 썼다. 쓰기를 따라가지 못하고 멈출 때 남은 것을 버렸다 |
| 4 (`part1.sh`) | 컨테이너 안(`/tmp`)에 쓰고 멈춘 뒤 꺼냄 | 20,062 대 20,060 | 버린 패킷 0 |

PostgreSQL은 네 번 모두 서버 로그와 2개 차이였다(캡처하는 바이트가 MySQL의 7분의 1이다).
캡처 파일을 호스트 폴더에 바로 쓰는 것이 느렸다. 도커 데스크톱의 파일 공유(virtiofs)를 거친다. 운영에서는 로컬 디스크에 쓸 것이다. 확인하지 않았다.

두 번째 차례에서 도구의 결함 하나를 찾았다. 놓친 연결의 뒤 조각을 "시작을 보지 못한 연결"로 한 번 더 셌다(4 + 4). 놓친 연결을 기억해 두게 고쳤다.

## 2부: 캡처의 부담

속도 제한 없이 8개 연결로 30초, 끔과 켬을 번갈아 5번. 처리량(초당 트랜잭션)이다.

| 차례 | 설정 | MySQL 끔 → 켬 (중앙값) | PostgreSQL 끔 → 켬 (중앙값) | 쓸 수 있는가 |
|---|---|---|---|---|
| 1 (`run.sh`, 10-15) | 캡처를 호스트 폴더에 씀 | 1,477 → 1,342 (-9.1%), 쌍마다 -5.5~-9.3% | 5,292 → 4,607 (-12.9%), 쌍마다 -20.6~+9.5% | 아니다. 캡처 파일이 30초에 300MB였다. 다 뜬 세 번째 설정에서는 1.8GB다. tcpdump가 대부분을 버리고 있었다 |
| 2 (10-17) | 컨테이너 안에 쓰고 멈출 때마다 파일을 꺼냄 | 끔 643, 1,226, 703 / 켬 981, 1,287 (도중에 멈춤) | - | 아니다. 1GB 넘는 파일을 꺼내는 디스크 쓰기가 다음 "끔" 실행에 얹혀 켠 쪽이 더 빨랐다(`out/first/part2-copy-bleed.log`) |
| 3 (`part2.sh`, 10-17) | 컨테이너 안에 쓰고 꺼내지 않음, 실행마다 20초 쉼 | 1,420 → 1,351 (-4.9%), 쌍마다 +6.1, -8.9, -8.0, +12.2, -3.7% | 5,248 → 1,712 (-67.4%), 쌍마다 -51.7, -69.9, +130.5, +9.4, -71.0% | 아니다(아래) |

세 번째는 장비가 두 상태를 오갔다. PostgreSQL은 끈 쪽도 5,200~5,900과 2,200~2,400으로, 켠 쪽도 5,000~5,700과 1,100~1,700으로 갈렸다.
MySQL은 네 번째 쌍이 끔과 켬 모두 450~506으로 무너졌다(p95 40ms). 캡처와 상관없이 나타나는 상태라 끔과 켬의 차이로 읽을 수 없다.
결과를 본 뒤의 분류지만, 두 실행이 모두 정상(MySQL 1,400 이상, PostgreSQL 5,000 이상)인 쌍만 보면 MySQL은 2, 3, 5번째 쌍의 -8.9, -8.0, -3.7%,
PostgreSQL은 4번째 쌍의 +9.4% 하나다.

같은 현상(실행 도중 DB가 무너지고 지나가면 돌아온다)이 실험 17에도 있었다. 무너진 때의 원인은 찾지 못했다. 도커 가상 머신의 입출력 압력(PSI)
누적값에 모든 작업이 입출력에 묶여 멈춘 시간이 442초 쌓여 있었다(10-17). 큰 파일을 지우는 일(캡처 파일, 바이너리 로그)이 입출력을 막는다고
짐작하지만 확인하지 않았다. 무효인 실행을 가리는 기준을 #99(실험 21)에서 정했다. 짐작과 달리 큰 파일을 지우는 일은 원인이 아니었고, DB와 상관없는 디스크 탐침을 기준으로 쓴다. 2부는 그 기준으로 다시 잰다(#106).

재기 전에 정한 판정(#79): 처리량 감소가 서버 로그(12%, 16%)보다 작고 5% 안이면 원문 대조 3번을 "방식이 다름"으로, 서버 로그보다 작지만 5%를 넘으면
"부분"으로 두고 수치를 적는다. 서버 로그 이상이면 목표를 채우지 못한다.

## 한계

- 캡처를 DB와 같은 장비, 같은 도커 가상 머신에서 했다. 운영에서 미러 포트나 다른 장비로 뜨면 DB 장비의 부담은 없을 것이다. 그 경우는 재지 않았다.
- TLS 연결은 읽지 못한다. 이 실험의 연결은 전부 암호화하지 않았다.
- 캡처를 켜기 전부터 열려 있던 연결은 읽지 못한다(연결의 시작을 봐야 메시지의 경계와 계정, 데이터베이스를 안다). 연결을 오래 붙들어 두는 연결 풀이 있으면
  캡처를 켠 뒤 새로 맺은 연결만 녹화된다. 이 실험은 부하를 캡처를 켠 뒤에 걸었다.
- 걸린 시간은 캡처한 장비에서 본 요청부터 마지막 응답까지라 서버 로그의 시간보다 길다(중앙값 MySQL 43 대 63µs, PostgreSQL 30 대 151µs).
- 1부는 설정마다 한 번이다.
