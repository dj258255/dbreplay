# 실험 24: 읽기만 틀 때 늦은 문장이 그 자리에서 새 연결을 연 탓인가

2026-10-19, MySQL 8.4 (도커, Apple Silicon 노트북, 도커에 CPU 12개). #119.

실험 23에서 DB 없이 돌린 재생기는 64배속까지 막히지 않았다. 진짜 MySQL에 틀면 15~20배속에서 막힌다(실험 22).
문장 단위 재생은 풀에 쉬는 연결이 없으면 그 자리에서 새 연결을 열고, 늦음은 연결을 받은 뒤에 잰다.
그래서 연결을 여는 시간이 늦음에 그대로 들어간다. 이것이 늦은 문장의 주된 까닭인지 쟀다.

## 결론

- **늦은 문장 가운데 그 자리에서 새 연결을 연 문장은 1~4%였다(16배속, 세 번).** 재기 전에 #119에 적은 기준으로
  **"주된 까닭이 아니다"**다. 16배속의 늦은 비율은 17~56%(중앙값 32%)로 실험 22를 재현했다.
- **다만 재기 전에 보지 못한 것이 나왔다. 모든 라운드에서 풀이 상한인 연결 500개를 다 열었다.** 4배속의 데우기 라운드도 그랬다.
  연결 하나를 여는 데 중앙값 14~123ms, 최대 233ms가 걸렸다. 문장 하나는 1ms가 안 걸리는 읽기다.
  풀이 가득 차면 나머지 문장은 연결이 돌아오기를 세마포어에서 기다린다(`SessionPool.acquire`). 그 기다림도 늦음에 들어가지만
  F는 연결을 직접 연 문장만 센다. 그러니 이 실험은 "연결 여는 시간이 직접 늦음을 만드는가"에 아니라고 답할 뿐,
  "연결을 여는 일이 풀을 막아 늦음을 만드는가"에는 답하지 않는다. 판정은 바꾸지 않는다. 뒤의 물음은 따로 잰다.
- **풀이 동시에 여는 연결을 4개로 묶은 뒤(#121) 다시 쟀다.** 16배속의 늦은 비율이 14~19%(중앙값 17.8%)로 내려갔다.
  고치기 전은 중앙값 32.1%였다. 재기 전에 #121에 적은 기준(10% 이하 / 25% 이상 / 사이)으로 **"일부만 설명한다"**다.
  연 연결은 라운드마다 139~299개, 하나를 여는 데 중앙값 2~8ms였다. 24배속은 47~56%로 거의 그대로다.

## 다시 돌리는 법

```sh
../22-workers/run.sh      # 트래픽 파일이 없으면 먼저. out/prod.trace.jsonl을 남긴다
caffeinate -i ./run.sh    # 약 3분. REPEAT=3이 기본이다. 결과는 out/. 끝나면 컨테이너를 지운다
OUT=out/limited-opens caffeinate -i ./run.sh   # #121의 두 번째 실행. 풀을 고친 빌드로
caffeinate -i ./progress.sh   # #127. replay --progress로 16배속의 매초 상태를 남긴다. 결과는 out/progress/
python3 summarize.py      # 판정을 다시 찍는다. OUT=out/limited-opens를 앞에 붙이면 두 번째 실행
```

`Bench.java`는 공개된 `Replayer.run`과 `JdbcTarget`을 그대로 부르고, 대상에 겉을 하나 씌워 연결을 연 스레드를 표시한다.
문장 단위 재생에서는 연결 받기, 실행, 결과 받기가 한 가상 스레드에서 차례로 일어나므로(`Replayer.runAlone`), 결과를 받을 때
그 표시를 읽으면 그 문장이 새 연결을 열었는지 안다. 미리 여는 연결 16개는 넘겨주는 스레드에서 열려 세지 않는다.

## 조건

- 구성: 실험 22와 같다. MySQL 8.4, sbtest 4×10만 행(sysbench prepare), `max_connections=1000`. 슬로우 로그는 끈다.
- 트래픽: 실험 22의 녹화(sysbench oltp_read_write, 초당 200, 연결 8개, 30초). 읽기만 남기면 84,463문장이다.
- 옵션: `Replayer.Options.atSpeed(s).onlyReads()`. explore `--only reads`와 같다(연결 상한 500, 미리 여는 연결 16개).
- 재생기는 DB와 같은 도커 네트워크의 실행 이미지(`../runner`)에서 돈다. explore가 아니라 직접 부르므로 지표를 뜨는 연결이 없다.
- 4배속을 한 번 데운 뒤(세지 않음) 8, 16, 24배속을 한 바퀴로 세 바퀴 돌았다. 라운드마다 풀을 새로 만든다. explore와 같다.

## 읽은 것

- 재생에 필요한 연결은 많지 않다. 16배속은 초당 읽기 약 4만 4천 개이고, 문장 하나가 0.2ms 걸리면 동시에 9개 남짓이면 된다.
  그런데 풀은 매번 500개까지 열었다. 순간적으로 미리 연 16개를 넘는 문장이 몰리면 그 문장들이 저마다 새 연결을 연다.
  연결을 여는 동안(수 ms) 도착한 문장도 쉬는 연결이 없어 또 연다. 동시에 여는 연결이 많을수록 하나를 여는 데 더 오래 걸린다
  (8배속 셋째 바퀴 14ms, 16배속 72~86ms). 이렇게 스스로 커지는 고리로 보지만, 고리가 있다는 것을 직접 잰 것은 아니다.
- 실험 22의 explore 기록에서 active_sessions가 133~276까지 튄 라운드가 있었다. 풀이 연 연결이 한꺼번에 실행 중으로 잡힌 것과
  맞아 보인다. 이 실험에는 지표를 뜨는 연결이 없어 맞대지 않았다.
- 8배속은 바퀴마다 줄었다(9.1 → 4.3 → 2.1%, 연 연결 500 → 437 → 379). 데워질수록 줄어든 것으로 보지만, 한 번 돌린 것이라
  우연과 가르지 못한다.
- 풀을 고친 뒤 16배속은 세 번이 14~19%로 모였다(고치기 전 17~56%). 500개를 여는 고리가 퍼짐을 키웠던 것으로 본다.
  8배속은 오히려 조금 늘었다(중앙값 4.3 → 6.1%). 자리가 찬 문장이 1ms씩 기다리는 것이 늦음에 들어간 것으로 보지만 재지 않았다.
- 고친 뒤에도 연결은 라운드마다 139~299개 열렸다. 어림한 9개보다 훨씬 많다. 문장이 실제로 얼마나 걸렸는지, 동시에 몇 개가
  실행 중이었는지는 재지 않았다. 남은 늦음(16배속 18%, 24배속 52%)이 어디서 오는지는 아직 모른다.

## 한계

- F는 연결을 직접 연 문장만 센다. 풀이 가득 차 기다린 문장, 연결을 여는 데 CPU를 빼앗겨 늦은 문장은 세지 않는다.
- explore를 통하지 않았다. explore는 라운드 사이에 지표를 뜨고 되돌리기 명령을 부른다. 이번에는 라운드 사이가 비어 있다.
- 같은 장비에서 한 번 돌렸다(배속마다 세 번).
