# 실험 08: 위탁해 둔 대상을 훑어 필요한 것만 다시 평가하는가

2026-10-12, MySQL 8.4.11과 PostgreSQL 16 (도커, Apple Silicon 노트북). 한 번 돌렸다.

메이투안의 시스템은 등록해 둔 클러스터의 평가가 만료되거나 무효가 되면 자동으로 다시 평가한다. 그 일을 하는
`dbreplay manage`를 두 기종의 대상 하나씩으로 확인했다(#6).

## 결론

- **처음에는 둘 다 평가하고, 바로 다시 돌리면 둘 다 그대로 두고, 한쪽의 파라미터를 바꾸면 그쪽만 다시 평가한다.**
- **다시 평가한 이유가 출력에 남는다.** `innodb_io_capacity 10000 → 2000`.

## 다시 돌리는 법

```sh
./run.sh                 # 약 7분
docker compose down -v
```

대상 목록은 `targets.json`이다. 대상마다 이름, 평가 파일의 위치, `explore`에 줄 옵션을 적는다.

## 결과

| 단계 | orders-mysql | shop-postgres |
|---|---|---|
| 1) 처음 | 평가. 상한 11.00배속, 수위 9% | 평가. 상한 14.00배속, 수위 7% |
| 2) 바로 다시 | 그대로 | 그대로 |
| 3) MySQL의 `innodb_io_capacity`를 바꾼 뒤 | 다시 평가. 상한 12.00배속, 수위 8% | 그대로 |

원자료는 `out/manage-1.txt`, `out/manage-2.txt`, `out/manage-3.txt`에 있다.

3단계에서 MySQL의 상한이 11.00에서 12.00이 됐다. 파라미터를 바꾼 효과라고 읽으면 안 된다. 같은 조건에서도 상한이
7.5에서 14까지 흔들린다(실험 03).

## 글과 다른 것

- 글의 시스템은 평가 큐가 떠 있고 만료를 스스로 알아챈다. 이 도구는 명령을 돌린 순간에만 본다. 주기적으로 보려면
  cron 같은 것에 걸어야 한다.
- 글은 위탁할 대상을 "트래픽 모양이 안정적인 핵심 클러스터"로 제한한다. 이 도구는 무엇을 등록할지 판단하지 않는다.
  목록에 적힌 것을 전부 본다.
- 무효 조건 넷 가운데 하드웨어 사양은 확인하지 못한다.

## 한계

- 한 번 돌렸다. 만료(30일)로 다시 평가되는 경우는 단위 테스트로만 확인했다.
- 트래픽 모양이 바뀐 경우를 만들어 보지 않았다. 같은 트래픽 파일을 계속 썼다.
- 대상이 둘이다. 여러 대상을 차례로 평가하므로 대상이 많으면 한 바퀴가 길어진다.
