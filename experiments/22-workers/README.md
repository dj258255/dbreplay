# 실험 22: --workers로 나누면 읽기만의 탐색에서 재생기의 한계가 오르는가

2026-10-18, MySQL 8.4 (도커, Apple Silicon 노트북, 도커에 CPU 12개). #113.

실험 07에서 읽기만 문장 단위로 튼 탐색은 네 번 모두 12배속 위에서 재생기가 먼저 막혔다. 알람은 한 번도 울리지 않았다.
#81에서 한 프로세스 안에 재생기를 여러 개 띄우는 `--workers`를 넣었지만, 그것으로 한계가 오르는지는 재지 않았다.

## 결론

- **`--workers 4`로 나누자 재생기의 한계가 오히려 내려갔다.** 다섯 번씩 번갈아 돌려 `--workers 1`은 15~20배속(중앙값 16),
  `--workers 4`는 3.75~11배속(중앙값 10)에서 재생기가 먼저 막혔다. 열 번 모두 알람은 울리지 않았다.
  재기 전에 #113에 적은 기준으로 **"오르지 않는다"**다. 읽기만 늘 때의 상한은 이 장비에서 여전히 "15배속 이상"까지만 안다.
- 원인 후보 하나(재생기마다 도는 `SpinTimer`)를 고쳐 다시 쟀다(#115). 재생기들이 타이머 하나를 함께 쓰게 하자
  `--workers 4`가 11~18배속(중앙값 15)으로 올랐다. 같은 실행의 `--workers 1`은 11~20배속(중앙값 19)이었다.
  `--workers 4` ÷ `--workers 1`의 중앙값이 0.63배에서 0.79배가 됐다. 재기 전에 #115에 적은 기준으로 **"타이머가 일부만 설명한다"**다.
  나눈 쪽이 하나보다 낫지는 않다. #113의 기준으로는 여전히 "오르지 않는다"다.

## 다시 돌리는 법

```sh
./run.sh                 # 약 15분. PAIRS=5가 기본이다. 결과는 out/
OUT=out/shared-timer caffeinate -i ./run.sh   # #115의 두 번째 실행. 공유 타이머가 든 빌드로
python3 summarize.py     # 판정을 다시 찍는다. OUT=out/shared-timer를 앞에 붙이면 두 번째 실행
docker compose down -v
```

노트북의 덮개를 닫으면 배터리로 돌 때는 `caffeinate`로도 잠드는 것을 막지 못한다. 잠들면 `summarize.py`가 그 탐색을 무효로 한다.

## 조건

- 트래픽은 실험 07과 같다. sysbench `oltp_read_write`를 초당 200, 연결 8개로 30초 녹화했다.
- `explore --only reads --workers W --alarm-metric "active_sessions>=32" --max-speed 64`를 W=1과 W=4로 번갈아 돌렸다.
  `--only reads`는 문장 단위로 튼다. 데이터가 바뀌지 않아 되돌리기는 건너뛰었다(`--reset-command true`).
- 내장 알람만 쓴다. 바깥 알람 명령은 과부하에서 표본을 읽지 못했다(실험 20, #109).
- 디스크 탐침(#99)을 함께 띄웠다. 판정 기준은 재기 전에 #113에 적었고 `summarize.py` 머리에도 있다.

### 무너진 첫 시도 (`out/shared-timer-slept/`)

공유 타이머로 처음 돌린 실행(14:57~)은 무효다. 15:00:28에 노트북의 덮개가 닫혀 장비가 잠들었다(`pmset-sleep.txt`, 배터리 사용 중).
탐색 하나가 17분, 1시간 42분씩 걸렸고, 1배속에서 "버티지 못했다"는 값이 나왔다. 잠들기 전에 끝난 두 탐색(15, 9.5배속)도
조건마다 셋이 되지 않아 쓰지 않았다.

- 그때의 무효 규칙(탐침이 느린 초가 30초 넘게 이어짐)은 잠든 구간을 잡지 못했다. 잠든 동안에는 표본 자체가 없기 때문이다.
  그래서 탐침의 표본 사이가 5초 넘게 비면 무효로 하는 규칙을 더했다. 판정 기준은 바꾸지 않았다. 첫 실행(#113)의 판정은
  이 규칙을 넣어도 그대로다(가장 긴 빈틈 1~2초).
- 이 실행의 탐침 기록은 남지 않았다. 실행을 멈출 때 `run.sh`의 trap이 탐침 컨테이너를 지운 뒤, 작업 세션이 `docker logs`를 다시
  받다가 빈 응답으로 파일을 덮어썼다. 지우기 전에 뽑아 둔 빈틈(527초, 468초, 3,446초, 2,655초)만 `disk-probe.txt`에 옮겼다.

## 읽은 것

- 첫 실행 뒤 원인 후보를 셋 적었다.
  1. 재생기마다 `SpinTimer`가 하나씩 있다. 이 타이머는 코어 하나를 쉬지 않고 돌린다(`SpinTimer.java`의 주석).
     `--workers 4`이면 넷이 돌아, 재생기와 DB가 나눠 쓰는 도커의 CPU 12개 가운데 넷이 시계만 본다.
     **고쳐서 다시 쟀다(#115). 일부만 설명한다.** 1배속에서 늦은 문장이 많던 것은 사라졌다.
  2. 재생기마다 트래픽 파일 전체를 읽고 해석한 뒤 제 조각만 남긴다(`TraceReader`의 `keep`). 해석이 네 번 일어난다.
  3. 조각이 고르지 않다. 원본의 연결 22개를 번호의 해시로 나눠 조각마다 레코드가 25%, 12.5%, 25%, 37.5%였다.
     다만 가장 큰 조각도 전체의 37.5%라, 재생기 하나의 한계가 그대로라면 나눈 쪽이 올라야 한다. 내려간 것을 설명하지 못한다.
- 남은 후보 2와 3은 재지 않았다.
- 그래서 `--workers`를 "재생기가 먼저 막힐 때 쓴다"고 안내하는 것은 이 장비에서는 틀렸다. 공유 타이머를 넣은 뒤에도 한 장비
  안에서 나누는 것은 하나보다 낫지 않았다. 장비를 나누는 `replay --shard`는 재지 않았다.

## 한계

- 원본 DB, 대상 DB, 재생기가 모두 한 노트북의 도커 안에 있다. 재생기를 나눠도 같은 CPU를 나눠 쓴다.
  재생기를 다른 장비에 두거나 장비마다 `replay --shard`로 나눈 것과는 다르다.
- `--shard`(프로세스 여러 개)는 재지 않았다.
- PostgreSQL에서는 돌리지 않았다.
